# Forge and Fabric Feature Audit

## How This Document Was Produced

This document was generated by an automated audit of the live Forge and Fabric codebase (repository root `c:/CYBERSOFT/forge-flow-main`, deployed at forge-fabric.vercel.app) on August 28, 2026. Every feature, table, function, route, and behavior described below was verified by reading the actual source files, SQL migrations, and edge function code that implement it, not by reading product plans, marketing copy, or prior documentation. Two planning documents exist in the repository, `DESIGN.md` and `Forge_Fabric_REQ14_REQ15_Implementation_Plan_v2.md`, and both were read, but they were treated only as a statement of intent. Every claim taken from them was checked against the code that actually runs today, and every place where the plan and the code disagree is called out explicitly.

Where a feature is only partially built, where a function is a stub, where sample or fallback data is shown in place of real data, or where an error is silently swallowed instead of being fixed or surfaced, this document says so directly in a Known Gaps subsection. Nothing below should be read as a claim that a feature is finished unless it is stated plainly as finished.

Every technical claim carries a file path, and in most cases an exact function, table, or component name, so any statement here can be checked by opening that file.

## 1. Repository Inventory

### 1.1 Route Tree

**In plain terms:** The application has 47 distinct web pages. About half are public marketing or legal pages anyone can open without an account. The rest sit behind a login screen, and which of those a given employee or customer can actually reach depends on their role, although that check happens after the page has already started to load rather than before.

**Technical detail:** Forge and Fabric uses TanStack Router in file based mode. Every route file lives directly under `src/routes/`, and the dot in a filename encodes nesting (for example `orders.$orderId.tsx` is a child of `orders.tsx`). A full grep of the route tree for `beforeLoad` or `loader`, the two mechanisms TanStack Router provides for gating a route before it renders, returns zero matches anywhere in `src/routes/`. Every access check in the application is implemented inside the rendered component itself, either as a `useEffect` that calls `navigate()` once the component has already mounted, or as conditional rendering driven by `usePermission()`. This means a user who is not supposed to see a page still has that page's component mount and its first render execute before any redirect fires.

Global providers are wired once in `src/routes/__root.tsx` and `src/router.tsx`. The provider order is `QueryClientProvider` wrapping `AuthProvider` wrapping an `AuthGate` component (which only delays rendering until the auth check resolves, it does not block by role) wrapping `AppDataProvider` wrapping the page itself.

Six of the 47 routes have a real, working redirect once the component mounts.

| Route | Guard | Effect |
|---|---|---|
| `/account` | `src/routes/account.tsx` | Redirects to `/login` if there is no user. |
| `/dashboard` | `src/routes/dashboard.tsx` | Redirects to `/login` if there is no user, and redirects any non admin user to `/qc`, `/orders`, or `/materials` depending on role. |
| `/orders` | `src/routes/orders.tsx` | Redirects to `/login` if there is no user, and redirects a `production` role user to `/materials`. |
| `/settings` | `src/routes/settings.tsx` | Redirects to `/login` if there is no user, and redirects any non admin user to `/dashboard`. This guard does not protect its own child routes, `/settings/branding` and `/settings/users`, because `SettingsRouteComponent` returns the child `Outlet` before the guarded `SettingsPage` component ever mounts. |
| `/submissions` | `src/routes/submissions.tsx` | Redirects a `customer` role user to `/orders`. |
| `/wash` | `src/routes/wash.tsx` | Redirects to `/login` if there is no user, and redirects any role other than `admin`, `production`, `qc`, or `customer` to `/orders`. |

Every other route, including operational pages such as `/cutting`, `/sewing`, `/qc`, `/dispatch`, `/inventory`, `/materials`, `/boms`, `/size-ranges`, `/sku-mapping`, `/styles`, `/finance`, `/reports`, and `/settings/branding` and `/settings/users` themselves, has no page level guard at all. Access control on those pages is limited to `usePermission()` calls that hide or disable individual buttons, so a person who can reach the URL can always see the page and its data, and can act on it if a button happens not to be hidden.

### 1.2 Database Schema

**In plain terms:** The system runs on a Postgres database managed through Supabase, built up over 60 separate migration files between mid July and the end of August 2026. Because the schema grew incrementally, some concepts ended up represented in more than one table. There are, for example, three separate representations of a purchase order (`orders.PO_number`, `blanket_pos`, and `purchase_orders`), and two separate customer master tables (`customers` and `companies`), and the shop floor pages read the older, simpler tables rather than the newer ones built for a fuller ERP model. This is described in detail below because it matters for anyone trying to build a report or an integration against the correct table.

**Technical detail:** The tables below are grouped by function. Column lists reflect the final state after all 60 migrations, not the original `CREATE TABLE` statement.

**Identity and tenancy.** `customers` (legacy CRM table, `id, name, contact, billing_address, shipping_address`) and `companies` (`id, name, code, tax_id, company_type, status, legacy_customer_id, website`) are two parallel customer master tables with no enforced synchronization between them, linked only by an unenforced `legacy_customer_id` soft reference. `profiles` (`id` references `auth.users`, `email, role, customer_id, company_id, facility, is_portal_user, status`) is the anchor for every access check in the system and carries two separate foreign keys, `customer_id` into `customers` and `company_id` into `companies`, both of which application code must keep correct. `role_type` is a Postgres enum that originally held five values (`admin, merchandiser, production, qc, customer`) and was later extended with seven more (`super_admin, production_manager, cutting_supervisor, sewing_supervisor, qc_inspector, warehouse, finance`), so the system runs two overlapping role vocabularies at once, and neither the legacy nor the ERP values were ever retired. `contacts` and `address_book` round out the CRM layer, with `address_book.company_id` deliberately left without a foreign key constraint after `supabase/migrations/20260818000000_update_cut_tickets_schema.sql` dropped it, so seeded and legacy addresses can carry a plain text customer name instead. `tenant_config` (one row) is the live source for branding and operational limits shown in `/settings/branding`. A second, near identically named table, `tenant_branding`, also exists but no application code reads it, per an explicit comment in `supabase/migrations/20260823000000_v2_spec_production_upgrade.sql`. `audit_logs` is an append only log of admin actions (invite, role change, suspend, reactivate) with no update or delete policy at all.

**Intake and submissions.** `apply_submissions` is the raw record created by the public intake wizard, holding company and contact fields, `style_blocks` and `trim_components` as JSON, `requested_stages` as an integer array, `priority`, `rush_multiplier`, and a `status` column that has never had a database check constraint even though the application relies on eight distinct string values (`pending_review, under_review, approved, rejected, needs_info, converted, pending_customer_review, customer_rejected`). `apply_cut_sheets` carries the structured cut sheet data as a `sheet_data` JSON blob with `is_current`/`version` fields for revision tracking. `apply_documents`, `merchandiser_assignments`, and `notification_logs` round out the intake tables. `update_requests` has a documented schema drift problem: a second migration, `20260818000000_update_cut_tickets_schema.sql`, attempted to redefine it with an entirely different, incompatible column set using `CREATE TABLE IF NOT EXISTS`, which silently did nothing because the table already existed from an earlier migration, so the live table still uses the original 2026-07-14 column set and the later migration's intended columns never landed.

**Orders and purchase orders.** `orders` is the table every shop floor screen actually reads and writes, keyed by a free text `order_id`, with `current_stage`, `status` (`Open, In Production, On Hold, Shipped`), `selected_stages` as an integer array, `priority`, `is_sample`, and `created_date` stored as plain text rather than a real date type even though five different trigger functions parse it with `to_timestamp()`. `blanket_pos`, `work_orders`, `purchase_orders`, and `po_line_items` form a separate, more properly normalized ERP model, but an explicit code comment in `src/hooks/useAppData.tsx` states plainly that this second model is "a separate, disconnected schema that no live shop-floor page (cutting/sewing/qc/dispatch) reads." In practice, converting a submission creates a `blanket_pos` row for bookkeeping, and the actual trackable production order is a second, separate insert into `orders`.

**Product master data.** `size_ranges`, `styles`, `skus`, and `boms` form the style and bill of materials catalog. A second, earlier bill of materials concept, `bom_templates`, keyed by free text style and colorway rather than a real foreign key, still exists in the schema and still has row level security, but is confirmed unused by any frontend code.

**Sample requests.** `sample_requests` is the primary live sample request table, separate from `apply_submissions` rows where `submission_type = 'sample_request'`. Both paths feed the same merchandiser dashboard.

**Shop floor tables.** `materials` (legacy fabric and trim receiving), `cutting_records` (legacy cutting completion, still the table the database level stage gate reads), `cut_tickets` (the modern cut ticket record `cutting.tsx` actually writes), `bundles` (the barcode tracked cut bundle), `sewing_bundles` (legacy per order sewing progress), `sewing_tickets` (the modern sewing ticket record introduced specifically because, in the words of its own migration, "sewing.tsx has never had a real ticket concept, it was a barcode-scan page"), and `wash_batches` (wash and finish stage tracking) together implement the physical production flow. `equipment`, `qc_checkpoints`, and `size_ratios` are small configuration tables.

**Quality control.** `qc_records` is the legacy table the database level stage gate trigger actually reads. `qc_inspections` is the modern table `qc.tsx` writes to, and a trigger bridges every new `qc_inspections` row into `qc_records` so the gate still works. `rework_logs` captures the cost of poor quality data described in section 6.2, with `calculated_copq_usd` computed automatically by Postgres from labor time and scrap fabric.

**Outsourcing.** `stage_outsourcing_records` is the universal table tracking any stage sent to a vendor, and `outsource_return_qc` holds the individual inspection records for returned outsourced work.

**Inventory and materials.** `inventory_items` and `inventory_lots` form the modern, lot level inventory system with a database generated `available_quantity` column. `material_requisitions` and `inventory_issuances` support the older, separate ERP material planning model. A fully built, schema backed, realtime subscribed "Raw Materials Intake" feature, with its own table `raw_materials_intake` and its own React components (`src/components/materials/`), exists in the codebase but is never imported by any route, confirmed by grep, meaning a complete feature is entirely unreachable from the running application.

**Dispatch.** `packing_lists` and `cartons` drive the actual dispatch flow. `delivery_manifests`, a table for driver signature proof of delivery keyed to `work_orders`, was never adopted, confirmed unused.

**Notifications.** `notifications` is the in-app alert feed. Its foreign key to `orders` was deliberately dropped in `supabase/migrations/20260821000100_notifications_order_id_not_fk.sql` after a documented bug in which rejection notifications for a submission that had no backing order row were silently rejected outright by the constraint, meaning rejected applicants never received their notification.

Nine tables were confirmed, by a full repository grep for `.from('<table>')` returning zero matches, to be schema that was built and then never wired to any screen: `tenant_branding`, `migration_exceptions`, `bom_templates`, `sample_request_documents`, `material_inbound_expectations`, `material_sourcing_requests`, `qc_defect_logs`, `delivery_manifests`, and `size_gate_records`. All nine remain live in the schema with active row level security policies.

### 1.3 Row Level Security and the Role Model

**In plain terms:** Every table in the database is protected by rules, called row level security policies, that determine which logged in user can see or change which rows. Most of these rules are correct today. A small number of tables, however, still carry an old, wide open rule from earlier in the project's history that was never removed, meaning that for those specific tables, any visitor to the site, logged in or not, can currently read or write data that should be private. This is a real, current gap and is described precisely below rather than only in the summary section, because it affects how every stage and portal described later in this document should be understood.

**Technical detail:** Two dedicated migrations exist specifically to hunt down and close this exact pattern, `supabase/migrations/20260901000100_close_forgotten_anon_rls_holes.sql` and part of `supabase/migrations/20260823000000_v2_spec_production_upgrade.sql`. Postgres combines multiple permissive row level security policies on the same table with OR logic, so a single forgotten policy that says `USING (true)` overrides every other, correctly scoped policy on that table for that command. The cleanup migrations found and closed this pattern on `orders`, `cut_tickets`, `sewing_tickets`, `customers`, `materials`, `cutting_records`, `sewing_bundles`, `wash_batches`, `cartons`, and `notifications`. They did not check, and therefore did not close, the identical pattern on five other tables, which remain open as of the last migration in the repository, `20260901000500_fix_duplicate_ticket_rework_ordering.sql`.

The five tables with a confirmed, still open policy are:

| Table | Policy name | Effect |
|---|---|---|
| `profiles` | `profiles_select_clean` | Any visitor, logged in or not, can read every user's email, role, and company assignment. |
| `profiles` | `profiles_insert_clean` | Any visitor can insert a new profile row with an arbitrary role value, including `admin`. |
| `apply_submissions` | `apply_submissions_select_all` | Any visitor can read every customer intake submission, including contact details and internal notes. |
| `apply_submissions` | `apply_submissions_update_all` | Any visitor can modify any submission's status or assignment. |
| `bundles` | `bundles_full_access` | Any visitor has full read and write access to every cut bundle record. |
| `scan_events` | `scan_events_full_access` | Any visitor has full read and write access to every barcode scan event. |
| `inventory_issuances` | `inventory_issuances_full_access` | Any visitor has full read and write access to every material issuance record. |

The order and quote management research for this audit separately found the `apply_submissions_select_all` hole while investigating a different, already fixed issue on the `orders` table, and confirmed it is still present as of the newest migration. This should be treated as an active item, not a historical footnote.

Two functions do the actual permission checking inside most policies. `is_internal_staff()`, defined in `supabase/migrations/20260811000600_erp_rls_security_policies.sql` and last redefined in `20260823000000_v2_spec_production_upgrade.sql`, returns true if the caller has a non-deactivated profile whose role is anything other than `customer`. It is a coarse, all-or-nothing staff check and is what most tables in the system rely on. `has_module_permission(module, action)`, added in the newest migration, `20260901000200_role_granular_rls_matrix.sql`, is a hand written SQL copy of the same permission table defined in `src/lib/permissions.ts` on the frontend, covering nine of the ten modules the frontend defines. The migration's own comment lists the tables it did not get around to converting, `po_line_items, styles/skus, shipments, packing_lists, delivery_manifests, invoices`, which remain on the coarser `is_internal_staff()` check. Because the frontend matrix and this SQL copy are maintained by hand in two separate files with no automated link between them, a future change to one without the other would silently create a mismatch between what the interface shows a role and what the database actually allows that role to do.

A third function, `get_auth_user_company_id()`, is what most of the customer facing row level security policies use to scope a logged in customer to only their own company's rows.

### 1.4 Edge Functions

**In plain terms:** Twelve small server side programs, called edge functions, handle tasks that need to run with elevated database access rather than directly from a customer's or employee's browser, such as inviting a new user or sending an order confirmation email. Four of the twelve are not actually used by the running application today. Of the eight that are used, none of them verify who is calling them beyond checking that an authorization header is present at all, and three have no such check whatsoever, which is a meaningful security gap described in the summary at the end of this document.

**Technical detail:** All twelve live under `supabase/functions/`, each using the Supabase service role key, which bypasses row level security entirely.

| Function | Used by the app | What it does |
|---|---|---|

### 1.5 Database Functions and Triggers

**In plain terms:** Beyond the edge functions, a set of rules live directly inside the database itself, written in SQL, that automatically enforce business rules no matter which screen or tool is used to change the data. The most important of these is the rule that decides whether an order is actually allowed to move to its next production stage.

**Technical detail:** `enforce_order_stage_gates()`, a trigger on `orders` before every update, is the authoritative, database level stage gate. It has a complicated history: it was created once, then dropped entirely by `supabase/migrations/20260808000100_fix_all_rls_recursion_and_pipeline.sql` "to allow seeding & bulk sync," and did not exist again for roughly nine migrations, meaning for that period the only thing preventing an order from skipping stages was frontend logic that a direct database write could bypass. It was recreated from scratch in `20260825000000_selective_pipeline_and_enhanced_outsourcing.sql` and has been rewritten four times since to add checks for outsourced work return quality, cutting completion, sewing completion, and wash approval, most recently in `20260901000500_fix_duplicate_ticket_rework_ordering.sql`. Its current logic is described stage by stage in section 3.

`get_next_selected_stage()` and `get_prev_selected_stage()`, added in the same migration, walk an order's `selected_stages` array to find the next or previous stage in a customer's chosen pipeline, skipping any stage the customer did not select. These functions are never called directly from the frontend. A separate, independently maintained copy of the same logic, `getNextSelectedStage()` in `src/lib/utils.ts`, is what the interface actually uses, meaning the two must be kept in sync by hand.

`prevent_duplicate_cut_ticket()` and `prevent_duplicate_sewing_ticket()` block a second active ticket from being opened for the same work order unless the most recent quality inspection for that stage came back as a reject or a rework. Both were rewritten in the newest migration, `20260901000500_fix_duplicate_ticket_rework_ordering.sql`, to order by a real timestamp column rather than a day only text date, after a confirmed live incident in which ten same day inspection records for one order made the "most recent" pick unpredictable and incorrectly blocked a legitimate rework ticket.

`cascade_packing_list_shipped()` is the trigger that, when a packing list's status changes to Shipped, finds the matching order and moves it to stage 13 and status Shipped. It was rewritten once to fix a bug where an order that had already reached stage 13 by other means was silently excluded from the cascade by an overly narrow stage comparison.

`convert_submission_to_blanket_po()`, `customer_review_decision()`, `respond_to_price_quote()`, `get_submission_status_by_reference()`, and `convert_sample_to_work_order()` are the database functions behind the order and quote management features described in section 5, each covered there in detail.

`check_pp_sample_gate()`, intended to block a bulk order for a style until its pre-production sample is approved, is a stub that unconditionally returns true, with a comment stating real enforcement is deferred until a related column is more strongly typed.

### 1.7 Custom Hooks

**In plain terms:** The application's connection to the database is organized into about 24 reusable pieces of code called hooks, each responsible for one area, such as orders, outsourcing, or authentication. Most of them keep a live connection open so that when one person changes something, other people looking at the same data see it update automatically without refreshing the page.

**Technical detail:** `src/hooks/useAppData.tsx`, at 2,763 lines, is the central data hook, providing orders, materials, cutting, sewing, wash, quality control, cartons, and outsourcing data to nearly every internal screen. It queries roughly 18 tables through TanStack Query, and every entity has a parallel, local storage backed fallback path seeded from `src/lib/mockData.ts`, selected by a flag called `isRealSupabase`. That flag is defined in `src/lib/supabase.ts` and, because the file hardcodes a working Supabase URL and key as defaults, the flag is effectively always true in practice, so the fallback path is dormant rather than removed. The hook maintains one shared realtime subscription, channel `db-realtime`, listening for changes on `notifications, orders, qc_records, cartons, work_orders, stage_outsourcing_records, outsource_return_qc, blanket_pos, invoicing_records`, and `customers`, and every handler simply tells TanStack Query to refetch rather than writing the changed row directly into the cache. This same invalidate on change pattern, confirmed across all ten realtime subscriptions found in the codebase, is described further in section 11.3.

`useOutsourcing.ts` provides the dispatch, receive, and return quality control mutations described in sections 3 and 7. `useAuth.tsx` is the authentication provider, covered in section 11.4. `usePermission.ts` is a thin wrapper around the permission matrix in `src/lib/permissions.ts`. `useApplySubmission.ts` and `useApplyDraft.ts` power the customer intake wizard. `useConvertSubmission.ts` exists in two separate places, `src/hooks/useConvertSubmission.ts` and `src/hooks/merchandiser/useConvertSubmission.ts`, and only the second, merchandiser namespaced one is actually imported anywhere; the first is dead code that still contains a hardcoded $24.50 per unit price, described in section 5.4. `useCutSheetParser.ts` handles spreadsheet import and export for cut sheets. `useSkuMappings.ts` and `useStageJumpLogs.ts` support the SKU mapping and stage override audit trail screens. `useRawMaterialsIntake.ts` is fully built and realtime subscribed but, as noted in section 1.2, is never imported by any route. The `src/hooks/merchandiser/` subdirectory holds six further hooks for the submissions inbox, cut sheet versioning, notifications, submission detail, and update requests, each covered in its relevant section below.

## 2. Roles and Permissions

**In plain terms:** The system recognizes ten distinct kinds of user. Two of them, super admin and admin, can do essentially anything. The rest are scoped to specific areas of the factory or to their own company's data if they are a customer.

**Technical detail:** `src/lib/permissions.ts` defines a `PERMISSION_MATRIX` covering ten modules (`admin, crm, product_master, orders, production_planning, shop_floor, qc, inventory, shipping, finance`) against each role, and `has_module_permission()` in `supabase/migrations/20260901000200_role_granular_rls_matrix.sql` is a hand maintained SQL copy of the same table for nine of those ten modules. The two legacy role values `production` and `qc` are normalized to `production_manager` and `qc_inspector` respectively by `normalizeRole()`, and an unrecognized role value falls back to `customer`, the most restricted role, rather than to anything more privileged.

| Role | Broad access |
|---|---|
| super_admin, admin | Full create, read, update, and delete on every module. |
| merchandiser | Full control of companies, contacts, styles, orders, purchase orders, sample requests, price quotes, and the tech pack vault. Read only on shop floor, quality control, shipping, and finance. Create, read, and update on inventory. |
| production_manager (legacy `production`) | Full control of shop floor tables (cut tickets, sewing tickets, cutting records, sewing bundles) and production planning. Read only on orders, quality control, and shipping. No finance access. |
| cutting_supervisor | Read on product master and production planning. Create, read, and update, but not delete, on shop floor. Read only on quality control and inventory. |
| sewing_supervisor | The same access pattern as cutting_supervisor, applied to the sewing floor. |
| qc_inspector (legacy `qc`) | Full create, read, and update, but not delete, on quality control only. No access to orders, inventory, shipping, or finance. |
| warehouse | Full control of inventory and shipping. Read only on companies. |
| finance | Intended full control of finance data, though the underlying `invoicing_records` database policy still literally checks for `admin` or `merchandiser` and carries a comment noting finance needs to be added, so this role's finance access is narrower in the database than the frontend implies. Read only elsewhere. |
| customer | No internal staff access anywhere. Scoped entirely to their own company's orders, purchase orders, sample requests, packing lists, invoices, and price quotes, matched through their `company_id`. |

Because both the legacy and ERP role name variants remain live simultaneously, and because some older, unconverted database policies still check the literal string `role = 'production'` rather than accepting both spellings, a user account stored with the modern `production_manager` value can, on those specific older tables, fail a check that a `production` labeled account would pass. This is a real, confirmed inconsistency, not a hypothetical one.

The customer role has two narrow exceptions that let a customer act without needing broad table access: `customer_review_decision()`, which lets a customer approve or reject an order a merchandiser drafted on their behalf, and `respond_to_price_quote()` together with `get_submission_status_by_reference()`, which let an anonymous visitor who knows a submission's reference code and the email on file check status or accept a price quote without logging in at all.

## 3. The Thirteen Stage Production Pipeline

Every order in Forge and Fabric moves through up to thirteen numbered production stages, from fabric receiving through dispatch. An order does not have to pass through every stage; which stages apply to a given order is controlled by the selective pipeline feature described in section 4. This section documents what each stage actually does in the code today.

### 3.1 Stages 1 to 3: Fabric and Trim Receiving and Inspection

**In plain terms:** Before anything can be cut, the raw fabric and trim for an order has to physically arrive at the factory, be logged against the correct purchase order, and pass a quality check. This is the paperwork and inspection step that unlocks everything downstream.

**Technical detail:** These three stages map to the `fabric_receiving` service group (internal stages 1 through 3) in `src/lib/service-scope-constants.ts`, and are implemented by the same two screens, `/materials` (`src/routes/materials.tsx`) and `/inventory` (`src/routes/inventory.tsx`), described in full in sections 8.1 and 8.2. Both write into the legacy `materials` table (`material_id, order_id, type, description, qty_received, inspection_status, received_date`) and, in parallel, into the newer `inventory_lots`/`inventory_items` tables. `inspection_status` can be `Pending, Approved`, or `Hold`.

Stage gate: `checkStageAdvancement(toStage=3, ...)` in `src/hooks/useAppData.tsx` requires at least one `materials` row to exist for the order at all. `checkStageAdvancement(toStage=4, ...)` requires every `materials` row for that order to be `Approved`, blocking on any row still `Pending` or `Hold`, and names the specific holding row in its error message. Only `admin, super_admin`, and `warehouse` roles may actually set a row to Approved (`canApproveReceiving` in both `materials.tsx` and `inventory.tsx`); any other permitted user attempting to submit an already Approved status is silently clamped back to Pending by the submit handler as a defense in depth measure.

Outsourcing does not apply to these stages; there is no material sourced from outside the factory to send to a vendor at this point.

Customer visibility: a customer sees this collapsed into the single friendly label "Fabric Receiving & Inspection" on their order progress view, with no internal table or column names shown.

**Known gaps:** The stage gate that requires all materials to be Approved before a materials receiving milestone can be recorded has no database level backstop today; it exists only in frontend logic in `useAppData.tsx`, per the documented history of `enforce_order_stage_gates()` in section 1.5, which does not check `materials.inspection_status` at all in its current form. `inventory.tsx` and `materials.tsx` each independently reimplement the same goods receipt submission logic, and the two copies have already drifted, described fully in sections 8.1 and 8.2.

### 3.2 Stage 4: Pre-Production Planning

**In plain terms:** Before cutting starts, someone has to plan how the fabric will actually be used, confirming the bill of materials for the style being produced.

**Technical detail:** Stage 4 is auto included whenever a customer selects the Cutting service (`service-scope-constants.ts`). There is no dedicated planning screen; the stage exists as a gate boundary and is satisfied by the same materials approval condition described above, since `checkStageAdvancement(toStage=4)` is the function that actually governs leaving stage 3 to enter stage 4. The `boms` table (section 8.4) is what a bill of materials actually looks like in the schema, but no code was found that ties a specific `boms` completeness check to this stage transition.

**Known gaps:** This stage has no dedicated user interface, and no code path was found enforcing that a bill of materials actually exists for a style before its order can proceed past this stage.

### 3.3 Stages 5 and 6: Cutting and Bundling

**In plain terms:** This is where fabric is physically spread in layers, a marker layout is cut through it, and the resulting garment panels are grouped into labeled, barcoded bundles by size, ready to travel to the sewing line.

**Technical detail:** Implemented entirely in `src/routes/cutting.tsx` (1,277 lines). Data lives in `cut_tickets` (the authoritative modern record, `ticket_number, work_order_id, marker_name, total_layers, yards_allocated, total_planned_pcs, total_actual_pcs, status, first_cut_approved, size_breakdown`), `bundles` (`bundle_barcode, size, quantity, colorway, status, current_stage_id`), and `cutting_records` (the legacy table the database trigger still reads, `status, first_cut_approval_status`).

Status values: `cut_tickets.status` is `"In_Progress"` on creation and `"Completed"` once the ticket is finished, set by `handleCompleteCutTicket()`. `bundles.status` is inconsistently written as `"Created"` on creation but the lowercase `"active"` on completion, which does not match the bundle record's own TypeScript type definition of `"Created" | "In_Progress" | "Passed" | "Rework"`.

Stage gate enforcement: on the frontend, `checkStageAdvancement(toStage=6, ...)` requires a `cutting_records` row with `status='Completed'` and `first_cut_approval_status='Approved'`. On the database, `enforce_order_stage_gates()` enforces the identical condition directly on any attempt to move `orders.current_stage` past 6, regardless of which screen or tool tried to make the change. A separate trigger, `prevent_duplicate_cut_ticket()`, blocks opening a second cut ticket for the same work order unless the most recent quality inspection for the First Cut Approval checkpoint came back Reject or Rework, and the frontend mirrors this exact rule client side before ever attempting the insert.

In house workflow, screen by screen: the page loads existing cut tickets as a filterable, searchable card grid. A Create Cut Ticket button, visible only to users with `shop_floor` update permission, opens a modal to select a work order, then a fabric lot (restricted to lots already marked Approved for that order's purchase order), marker name, total layers, yards required, shade lot, and an editable planned size breakdown pre-filled from the order's real size data. Submitting runs the gates described above in order, then inserts the ticket, the inventory issuance record, and generates bundle barcodes in the format `BND-{STYLE}-{SIZE}-{sequence}`. Each ticket card shows its generated bundle barcodes and, while still in progress, a Complete Cutting & Issue Bundles button that finalizes the ticket and writes the `cutting_records` row the stage gate actually checks.

Outsourced workflow: an order scoped `StageOutsourcingPanel`, filtered to stages 5 and 6, sits below the ticket grid for any non-customer user. If an active outsourcing record exists for these stages, in house ticket creation is disabled both visually and inside the submit handler itself. Returning outsourced work automatically creates a `Pending` row in `outsource_return_qc`, and the stage cannot advance until that row's inspector sets a result of `Passed` or `Partial_Pass`, with any resulting quantity shortage explicitly marked resolved through a separate action before the block clears.

Roles: `usePermission("shop_floor", "update")` gates ticket creation and completion, which per the permission matrix grants both `cutting_supervisor` and `sewing_supervisor` the identical ability to create and complete cutting tickets, since the check does not distinguish which floor a supervisor is assigned to. `usePermission("production_planning", "update")` separately gates the ability to dispatch or receive outsourced work, which cutting and sewing supervisors can see but not act on, since they only have read access to that module.

Customer visibility: a customer sees only a single collapsed step labeled "Cutting & Bundling," derived from `getStageFriendlyName()`, with a status of Complete, In Progress, or Upcoming. No bundle, panel, carton, or vendor routing detail is shown.

**Known gaps:** Every bundle barcode is generated purely from style, size, and a sequence number with no ticket instance suffix, so a second, legitimate cutting pass after a rework regenerates identical barcodes to the first pass, and both the create and complete handlers use an upsert on that barcode, silently overwriting the original bundle row rather than creating a distinguishable new one. Every insert of a cut ticket, inventory issuance, or bundle record that fails is caught and only logged to the browser console with `console.warn`, never surfaced to the user or rolled back, so a failed write can leave dependent records referencing a ticket that does not actually exist. The bundle's `current_operation_id` field is hardcoded to the literal string "Operation 01: Front Pocket Prep" at creation and never updated again as the bundle physically moves through real operations.

### 3.4 Stage 7: Sewing Assembly

**In plain terms:** Cut, bundled panels are assembled into finished, unwashed garments on a sewing line.

**Technical detail:** Implemented in `src/routes/sewing.tsx` (702 lines). Data lives in `sewing_tickets`, the modern authoritative record introduced specifically to replace what its own migration comment calls a page with "no ticket concept at all," and `sewing_bundles`, the legacy mirror table the database gate still falls back to for older orders that predate the ticket model.

Status values: `sewing_tickets.status` is `"In_Progress"` then `"Completed"`, set by `handleCompleteSewingTicket()`.

Stage gate enforcement: `checkStageAdvancement(toStage=8, ...)` checks whether the order has any `sewing_tickets` rows at all; if it does, every one of them must be `Completed`, and only if the order has zero `sewing_tickets` rows does the check fall back to the legacy `sewing_bundles` completeness check instead, a fallback that exists specifically because `cutting.tsx` writes a mirror `sewing_bundles` row as a side effect of completing a cut ticket, which would otherwise permanently block a genuinely finished, ticket based order. The database trigger `enforce_order_stage_gates()` implements the identical real table first, legacy fallback logic directly in SQL. Progress further requires an `"Inline Sewing QC"` inspection record with a result other than Reject. `prevent_duplicate_sewing_ticket()` blocks a second active ticket per work order unless the most recent Inline Sewing QC result was Reject or Rework, mirrored client side before submission.

In house workflow: the page computes which orders are actually eligible for a new sewing ticket, meaning cutting has been completed and approved and at least one real cut bundle exists, and disables the Create Sewing Ticket button entirely when no order qualifies, with a banner explaining why. The creation modal offers only eligible work orders, a line number, an operator count, and a read only planned size breakdown pulled directly from the order's real cut bundle output, with an explicit code comment stating the numbers are "never invented." Completing a ticket sets its status, records actual pieces produced, and advances the order's bundle records to stage 8.

Outsourced workflow: identical mechanics to cutting, scoped to stage 7, using the same `StageOutsourcingPanel` and return quality control gate.

Roles: gated identically to cutting, on `shop_floor` update permission, meaning a sewing supervisor can equally operate the cutting screen and vice versa.

Customer visibility: collapsed to the single label "Sewing Assembly."

**Known gaps:** This is the stage most directly affected by the barcode scanner rebuild, detailed in full in section 7.2, and the two systems described there, the modern ticket flow in `sewing.tsx` and the barcode kiosk in `tablet.tsx`, are confirmed to be entirely disconnected from one another.

### 3.5 Stage 8: Pre-Wash Quality Check

**In plain terms:** Before garments go to the laundry, an inspector checks a sample of the sewn output.

**Technical detail:** This stage corresponds to the "Inline Sewing QC" checkpoint referenced in the stage 7 gate above, and has no dedicated screen of its own; it is one of the five named checkpoints inspected through the shared `/qc` page (section 6 and 7). Two different, disagreeing sets of stage thresholds exist for this same checkpoint name in the codebase: `src/lib/qcGateValidation.ts` requires `current_stage >= 6` before this checkpoint can be logged when reached from the order detail page, while `qc.tsx`'s own separate, hand rolled gate logic requires `current_stage >= 5` for the identical checkpoint when logged from the QC screen directly. This is a genuine, unresolved inconsistency between two independent implementations of the same rule.

**Known gaps:** See the qc.tsx versus qcGateValidation.ts inconsistency above, documented fully in section 6.5.

### 3.6 Stage 9: Washing and Laundry

**In plain terms:** Sewn garments are washed, dried, and given their intended finish treatment at a physical laundry facility, using equipment such as industrial washers, lasers, ozone chambers, and spray booths.

**Technical detail:** Implemented in `src/routes/wash.tsx` (576 lines), which the route's own header literally labels "Stage 9 · 10 · 11," meaning this one screen covers washing, finishing, and part of final inspection all at once. Data lives in `wash_batches` (`batch_id, order_id, pcs_qty, stage, equipment_used`), where `stage` is an enum that walks `Wash → Dry → Finish → Approved`.

Stage gate enforcement, creation side: a new wash batch cannot be logged unless the order's `current_stage` is at least 8, quantity does not exceed the order's total, quantity is positive, and equipment is selected. Stage gate enforcement, advancement side: `checkStageAdvancement(toStage=10)` requires a batch at `Finish` or `Approved`, and both of these wash related gates are skipped entirely if a customer's `selected_stages` does not include stage 9, meaning washing simply is not part of that order's pipeline.

In house workflow: KPI tiles for pieces currently in wash versus finish versus complete, a visual four stage funnel computed from the in memory batch list, an editable batch table with inline status edits and a one step Advance button, and a Log Wash Batch modal restricted to orders already at stage 9 or 10.

Outsourced workflow: `StageOutsourcingPanel`, filtered to stages 9, 10, and 11, is embedded directly on this page twice. When an active outsourcing record exists for stage 9, the in house logging form is entirely disabled.

Roles: the route itself redirects any role other than `admin, production, qc`, or `customer` away to `/orders`. Within the page, only `admin` and `production` can edit records or log new batches; a `customer` can view but not act.

Customer visibility: a customer with route access sees the wash tracker but no outsourcing panel and cannot edit anything.

**Known gaps:** The stage dropdown on each batch row in the editable table allows an operator to jump directly to any stage value, including a reversal from Approved back to Wash, with no validation preventing that skip, separate from the intentional one step Advance button next to it. There is no database level backstop for any of these wash business rules; the trigger only enforces the outsourcing return quality gate at this point in the pipeline, described in section 3.11.

### 3.7 Stage 10: Finishing and Effects

**In plain terms:** This is where laser fading, ozone washing, spray treatments, or 3D wrinkle effects are applied to washed garments to achieve a specific look.

**Technical detail:** There is no dedicated finishing screen anywhere in the codebase. Finishing is folded entirely into `wash.tsx` as the `Finish` value of the same `wash_batches.stage` enum described above, and is governed by the exact same gate, workflow, outsourcing panel, and role restrictions as stage 9.

There is a confirmed, unresolved naming inconsistency involving stage 11: `wash.tsx` scopes its outsourcing panel to stages 9, 10, and 11 together, but `src/lib/outsourcing-constants.ts` defines stage 11 as "Final Quality Inspection," a checkpoint that conceptually belongs to quality control, not to wash and finishing. The database gate itself, `checkStageAdvancement(toStage=11)`, requires a wash batch at `Approved`, meaning the code's actual behavior treats stage 11 as a wash milestone, while the constants file used to build customer facing labels treats it as a QC milestone. Both cannot be fully correct at once, and this document does not attempt to resolve which was intended, only to record that the disagreement exists.

**Known gaps:** No dedicated screen exists for finishing as a distinct concept from washing. The stage 11 naming inconsistency above.

### 3.8 Stage 11: Final Quality Inspection

**In plain terms:** A final inspection of finished garments before they can be packed, intended to be an AQL style statistical audit.

**Technical detail:** As described above, this stage number is used two different ways in the codebase. `outsourcing-constants.ts` calls it "Final Quality Inspection" for customer facing labels. The actual gate function, `checkStageAdvancement(toStage=11)`, requires a `wash_batches` row at `Approved`, not any quality control record. The genuine final inspection checkpoint, named `"Final AQL-Packing Audit"` in the quality control code, actually gates stage 12 and 13 instead, described in sections 3.9 and 3.10.

**Known gaps:** This entire stage number is a naming and gate mismatch, carried over from section 3.7, and should be treated as unresolved rather than working as its label implies.

### 3.9 Stage 12: Pressing, Tagging and Packing

**In plain terms:** Finished, inspected garments are steam pressed, tagged, and packed into export cartons.

**Technical detail:** There is no dedicated screen for packing itself; carton records are created directly on the order detail page (`orders.$orderId.tsx`, `handleCartonSubmit`), always with `dispatch_status` hardcoded to `"Ready"` at creation, rather than on the `/dispatch` page, which only reads and updates existing cartons. Stage gate enforcement: `checkStageAdvancement(toStage=12)` requires a quality control record for either the `"Wash-Finish Approval"` or the `"Final AQL-Packing Audit"` checkpoint with a result of `Pass`.

**Known gaps:** There is an architectural mismatch between the module's name and where its actual functionality lives; despite `/dispatch` being labeled "Dispatch Logistics & Packing Lists," the carton and packing creation step it implies happens entirely on a different page.

### 3.10 Stage 13: Dispatch and Delivery

**In plain terms:** Finished, packed cartons are consolidated into an outbound shipment, assigned a carrier, and signed for by the driver, at which point the order is considered shipped.

**Technical detail:** Implemented in `src/routes/dispatch.tsx` (864 lines). Data lives in `packing_lists` (`packing_list_number, customer_name, po_number, destination_address, total_cartons, total_units, status, carrier_name, tracking_reference, pod_signature_ref, shipped_at`) and `cartons` (`dispatch_status`, either `Ready` or `Shipped`).

Stage gate enforcement, upstream requirement: `checkStageAdvancement(toStage=13)` requires a carton with `dispatch_status='Ready'` and a `"Final AQL-Packing Audit"` quality control record with result `Pass`. Downstream cascade: `cascade_packing_list_shipped()`, a database trigger, fires when a packing list's status becomes `Shipped`, matches the order by purchase order number or customer name, and sets the matched cartons to `Shipped` and the order to stage 13 and status `Shipped`. Critically, `dispatch.tsx` itself does not re-check the stage 13 upstream requirements before triggering this cascade; the proof of delivery confirmation flow trusts that the earlier gates were already satisfied and proceeds regardless.

A separate gate, the PO Prerequisite Gate, blocks dispatch entirely if a packing list has no purchase order number attached, enforced in three places: the creation form, the disabled state of the dispatch button itself, and a re-check inside the confirmation handler as a defense in depth measure.

In house workflow: a searchable card grid of packing lists, a Create Export Packing List modal (order selection auto-fills the customer and computes carton count from quantity divided by 30, destination from an address book, carrier as free text), and a Dispatch & Confirm Driver POD modal capturing driver name and a proof of delivery signature reference, auto-generated if left blank.

Outsourced workflow: none. No `StageOutsourcingPanel` appears anywhere on this page.

Roles: only `admin, super_admin`, and `warehouse` may create packing lists or confirm dispatch. A customer sees only their own company's packing lists and addresses, enforced both by database row level security, scoped by matching company name, and redundantly again in the frontend, with an explicit code comment stating the frontend duplication exists because certain hardcoded fallback data shown in offline mode never goes through a database query at all and row level security cannot protect it.

**Known gaps:** `dispatch.tsx` performs a client side duplicate of the database trigger's carton status update logic, with a comment explicitly acknowledging it exists as a workaround for "deployments where the trigger hasn't been applied yet," meaning two independently maintained implementations of the same cascade exist and could diverge. The stage 13 upstream requirements described above are not re-verified by this screen before it flips an order to Shipped.

### 3.11 The Universal Stage Gate Mechanism

**In plain terms:** Two separate systems work together to stop an order from skipping ahead or sliding backward through the pipeline improperly: one lives in the website itself and gives an immediate, friendly explanation of what is blocking progress, and a second, stricter one lives inside the database and cannot be bypassed no matter what tool or screen is used to try to change an order's stage.

**Technical detail:** The frontend layer is `checkStageAdvancement()` in `src/hooks/useAppData.tsx`, a single large function handling every stage transition from 1 through 13, called from the Kanban board, the order detail page, and the QC screen, and it is the source of the plain language "why is this locked" messages users actually see. The database layer is the trigger function `enforce_order_stage_gates()`, described stage by stage above and in section 1.5, which independently re-implements the material, cutting, sewing, and wash conditions in SQL so that a direct database write, bypassing the website entirely, is still stopped. A third, separate concern layered on top of both is the outsourcing return quality gate: whenever any stage's work was sent to an outside vendor, the order cannot leave that stage until the vendor's return has been inspected with a result of `Passed` or `Partial_Pass`, and any resulting quantity shortfall has been explicitly marked resolved with a written reason, a rule enforced identically by both the frontend and the database trigger.

**Known gaps:** The database trigger's own history includes a roughly nine migration period in which it did not exist at all, and even in its current, most complete form it only checks materials at stages 3 and 4 through the earlier, narrower legacy logic rather than the full seven condition set its original 2026-07-17 version had, meaning some of the original stage checks were never restored after the trigger was rebuilt from scratch. The wash stage's own status dropdown, described in section 3.6, can bypass the intended one step advancement even though the underlying gate itself is sound.

### 3.12 Known Gaps Across the Pipeline

- Stages 10 and 11 have an unresolved internal naming and gate mismatch, described in sections 3.7 and 3.8, where the label used for customers and the actual database condition checked do not agree on what stage 11 represents.
- Two different QC checkpoint gate threshold tables exist for the same five checkpoint names, one in `src/lib/qcGateValidation.ts` and one hand rolled directly inside `qc.tsx`, and they specify different minimum stage numbers for the identical checkpoint, described further in section 6.5.
- The barcode scanner kiosk at `/tablet` writes to a set of tables that the actual stage 7 to 8 sewing gate never reads, meaning actions taken on the kiosk can appear successful to the operator while having no effect on whether the order can actually advance. Full detail in section 7.2.
- Every write failure encountered while walking the pipeline code, across cutting, sewing, and wash, is caught and only logged to the browser console, never surfaced to the user, which means a user can be told an action succeeded when part of the underlying data was not actually saved.

## 4. The Selective Stage Pipeline (REQ-14 and REQ-15)

Rather than every order automatically running the full thirteen stage pipeline, a customer can choose which production services they actually want the factory to perform, described to them by plain service names rather than by internal stage numbers. This section covers that feature on its own, separate from the stage by stage documentation above, because it changes how the entire pipeline behaves for a given order.

### 4.1 How a Customer Selects Services

**In plain terms:** While filling out an order, a customer sees a set of named services, such as Cutting & Bundling, Sewing Assembly, Washing & Laundry, Finishing & Effects, and Pressing/Tagging/Packing, and simply checks the ones they want the factory to perform. Certain supporting steps, like receiving the fabric or a final inspection, are added automatically and are shown to the customer only as context, not as something they choose themselves.

**Technical detail:** The picker itself is `src/components/apply-portal/ServiceScopeSelector.tsx`, embedded in `StyleBlockEditor.tsx` at step 2 of the order intake wizard. It offers four preset shortcut buttons defined in `PRESET_SCOPES` (Full CMT, Sew plus Wash plus Pack, Wash plus Finish Only, and Custom) built from `src/lib/service-scope-constants.ts`, five individually toggleable service cards for the actual selectable services, and a chip row showing which supporting stages were automatically included and why, followed by a preview strip of the resulting pipeline order. No stage numbers appear anywhere in this interface's text. Toggling a service calls `resolveSelectedStages()`, which computes the final `selected_stages` array and writes it, along with the human readable `selected_services` list, onto the style block being edited. Per-service detail fields, such as marker requirements for cutting or wash process type for washing, appear conditionally directly below the picker only for the services actually chosen.

The identical friendly summary reappears on the public, no login order status page, `apply.status.$referenceCode.tsx`, in a "Your Requested Production Services" panel, and again on the internal submission detail panel a merchandiser reviews.

### 4.2 Storage, Validation and Consumption of selected_stages

**In plain terms:** The customer's choice is stored as a simple list of stage numbers on the order record, and that list is what the rest of the system checks whenever it needs to know whether a given stage even applies to this particular order.

**Technical detail:** `selected_stages` exists as an integer array column on both `orders` and `work_orders`, defaulting to all thirteen stages, and `apply_submissions.requested_stages` holds the same concept for a submission, left null rather than defaulted for legacy rows that predate this feature. A validation module, `src/lib/validation/stageSelection.ts`, defines Zod schemas requiring at least one stage, no duplicates, ascending order, and that stage 13 always be included, but a full search of the codebase confirms these schemas are never imported or called from anywhere outside their own file, so this validation, while written, does not actually run. There is also no database check constraint enforcing any structure on the `selected_stages` column itself.

Consumption is extensive. `getNextSelectedStage()` in `src/lib/utils.ts` and its database equivalent `get_next_selected_stage()` walk the array to find what stage comes next for a given order, skipping anything not selected. `checkStageAdvancement()` reads whether stage 9 is present in `selected_stages` before applying any of the wash related gates described in section 3.6, meaning an order that never selected washing simply skips those checks entirely. The order detail page reads it to grey out any stage not part of the order's chosen pipeline in the internal thirteen stage timeline, and to build the shorter, customer facing progress view. `StageOutsourcingPanel` filters its own stage dropdown to only the stages the order actually selected. The database trigger `enforce_order_stage_gates()` reads `OLD.selected_stages` directly to decide whether its outsourcing return quality check even applies to the stage an order is leaving.

### 4.3 The Friendly Name to Internal Stage Mapping

**Technical detail:** The mapping lives in `src/lib/service-scope-constants.ts` as `SERVICE_GROUPS`, and a second, largely matching copy exists in `src/lib/outsourcing-constants.ts` as `STAGE_FRIENDLY_NAMES`, used specifically by the Kanban board and the order detail customer view rather than the intake wizard.

| Friendly name | Internal stages | Customer selectable |
|---|---|---|
| Fabric Receiving & Inspection | 1, 2, 3 | No, auto-included with Cutting |
| Pre-Production Planning | 4 | No, auto-included with Cutting |
| Cutting & Bundling | 5, 6 | Yes |
| Sewing Assembly | 7 | Yes |
| Pre-Wash Quality Check | 8 | No, auto-included with Sewing |
| Washing & Laundry | 9 | Yes |
| Finishing & Effects | 10 | Yes |
| Final Quality Inspection | 11 | No, always included once any production service is chosen |
| Pressing, Tagging & Packing | 12 | Yes |
| Dispatch & Delivery | 13 | No, always included |

### 4.4 Invalid or Contradictory Service Combinations

**In plain terms:** Nothing in the running application today stops a customer from choosing a combination of services that does not make physical sense, such as requesting only finishing without ever requesting sewing or washing first.

**Technical detail:** This was checked definitively and the answer is no, there is no enforcement anywhere in the reachable code path. The Zod schemas described in section 4.2 that would catch this are written but never called. `resolveSelectedStages()` itself only adds supporting stages for what was chosen; it never checks whether a chosen combination is coherent, and a code comment inside that function states plainly that the plan's original idea of letting a customer supply their own pre-cut panels or raw fabric as an alternative to selecting Cutting was never implemented, because the underlying data model has no field to express it. `apply.new.tsx`, the intake wizard page itself, has no check blocking submission when zero services are selected or when the combination is illogical; the only feedback is a non-blocking amber warning line of text in the picker.

### 4.5 The Kanban Board

**In plain terms:** The main internal dashboard includes a card based board view of every active order, one card per order, grouped by how far along it is. The cards themselves are driven entirely by real, live order data. A separate chart elsewhere on the same dashboard page still falls back to fabricated sample numbers when there is no real data to show, which is a different problem worth being clear about.

**Technical detail:** The board lives in `src/routes/dashboard.tsx`, and every card reads from `useAppData()`'s live, Supabase backed `orders` collection, calling the same `checkStageAdvancement()` function described in section 3.11 to compute its own advancement status and lock reason. This part of the board carries no hardcoded or fabricated data. A planned redesign described in the project's own implementation plan, adding a service scope chip strip, an in house versus outsourced routing indicator, a return quality control badge, and a shortage badge directly to each card, was not implemented; the helper function that would generate the chip strip, `getServiceScopeChips()`, is imported into `dashboard.tsx` but never actually called anywhere in the file.

Separately, and on the same page, a different widget, the Brand Allocation bar chart in the dashboard's analytics summary area, falls back to four fabricated brand names and unit counts, matching the names of the seeded demo customers in `src/lib/mockData.ts`, whenever the real order data produces zero brand revenue to chart, for example on a genuinely new or empty database. This fallback is indistinguishable from real data in the interface.

### 4.6 The Conversion Flow

**In plain terms:** Once a merchandiser is satisfied with a submission's pricing and details, converting it turns the paperwork into a real, trackable production order.

**Technical detail:** The user interface is `src/components/merchandiser/ConversionModal.tsx`, and the actual mutation logic lives in `src/hooks/merchandiser/useConvertSubmission.ts`. Converting refuses to proceed at all if the contract quantity is zero or less. It registers the customer as a real company record if one does not already exist by name, updates the source `apply_submissions` row to status `converted`, syncs any merchandiser edits back onto the linked `apply_cut_sheets` record, and calls the `convert-submission-to-po` edge function, which in turn calls the database function `convert_submission_to_blanket_po()` to create the `blanket_pos` bookkeeping record described in section 1.2 and section 5.1. Separately, the modal's local order object, which carries the customer's chosen `selected_stages` and `starting_stage`, is written into the actual trackable `orders` table through `useAppData`'s own `addOrder()` mutation, independent of the edge function call. Every hardcoded placeholder value the platform's own implementation plan flagged for removal, a fabricated size matrix, a generic style name, a synthesized purchase order number, and a randomly generated work order number, was confirmed actually removed from this live path; the modal now requires each of those fields to be entered for real or shows a required field warning instead.

### 4.7 Known Gaps

- The Zod validation schemas written for `selected_stages` and `selected_services` are dead code, never imported outside their own file, so no combination checking actually runs today. See section 4.4.
- No enforcement exists anywhere preventing a customer from submitting, and having converted, an order that requests only a downstream service like Finishing without ever requesting Sewing or Washing.
- The Kanban board redesign described in the platform's own implementation plan, adding service scope chips, routing indicators, and quality control badges to each card, was not implemented; the helper function for it is imported but never called.
- The Brand Allocation chart on the same dashboard page shows fabricated brand names and revenue figures whenever real data is unavailable, with no visual indication that the numbers are not real.
- The public, no login order status page does not compute or show a real percentage complete progress bar tied to `current_stage`, despite the platform's own plan calling for one at that exact screen; the only place a true stage by stage Done, Current, Upcoming view exists is on the authenticated order detail page.
- A now dead, unused copy of the conversion hook, `src/hooks/useConvertSubmission.ts` at the top level of the hooks folder, still contains every hardcoded fallback value the platform's plan said to remove, including a synthesized purchase order number and a fixed size breakdown string, and remains in the repository even though nothing calls it.

## 5. Order and Quote Management

### 5.1 Blanket Purchase Orders

**In plain terms:** A blanket purchase order is the commercial contract record created once a customer's submission is approved, representing a total committed quantity a customer wants produced. It does not, by itself, create anything a factory floor employee can actually work from; that happens through a separate step.

**Technical detail:** `convert_submission_to_blanket_po()`, the database function behind conversion, inserts only a `blanket_pos` row, no longer inserting any `work_orders` row at all, a change made deliberately, with the responsible migration's own section header reading "FIX C.2: MERCHANDISER CREATION FLOW (NO AUTO WORK ORDERS)." The actual, trackable production order any shop floor screen can see is created separately, either by the merchandiser conversion hook inserting directly into `orders`, or, for a customer self-approved order, by the `customer_review_decision()` database function inserting its own `orders` row. What actually functions as a schedulable unit of work is the "Split into Batch" action on the order detail page, which calls `createOrderBatch()` to insert a child row directly into `orders` with a `parent_order_id` reference, a mechanism confirmed by an explicit code comment to be what work orders are meant to represent in this system, rather than the separate `work_orders` table. Cut and sewing tickets, described in sections 3.3 and 3.4, are generated independently, later, from the shop floor pages themselves, keyed to the real `orders.order_id`; nothing is auto-generated at the moment of blanket PO conversion.

Sample request conversion is architecturally different from bulk conversion: `convert_sample_to_work_order()` inserts into both `orders` and `work_orders` at once, meaning the sample path still writes to the disconnected `work_orders` table that the bulk path was deliberately changed to stop using, an inconsistency between the two conversion paths.

### 5.2 Merchandiser Created Orders and Customer Review

**In plain terms:** A merchandiser can start an order on a customer's behalf, for example after a phone call, and the customer then sees that draft order waiting for their sign off before anything moves forward.

**Technical detail:** A merchandiser uses the internal intake wizard at `/apply-intake`, the same components as the public wizard, which sets the submission's `status` to `pending_customer_review`, a value with no database check constraint, and records which staff member created it. The customer sees it in its own separate "Awaiting Your Approval" section of `/orders`, deliberately excluded from the normal active order list. Opening it takes them to `/orders/review/$submissionId`, a read only summary with Approve & Start Production and Request Changes buttons. Both actions call one database function, `customer_review_decision()`, which itself checks that the caller is genuinely a customer role whose own company matches the submission before doing anything. Rejecting requires a written reason. Approving requires a real, already known purchase order reference number to already exist on the submission, refusing to synthesize one, and requires the size matrix already on file to be non-zero, then calls `convert_submission_to_blanket_po()` and independently inserts the real, trackable `orders` row itself. This authorization check happens entirely inside the database function, since it runs with elevated privileges that bypass row level security, not through any table level policy.

### 5.3 Sample Requests

**In plain terms:** A customer can request a small sample before committing to a full production run. There are two separate ways a sample request can be created in this system, and they do not produce identically structured records, which matters for anyone trying to compare a sample's cut sheet against a bulk order's cut sheet.

**Technical detail:** Path one is through the public intake wizard, where a sample request is stored as an `apply_submissions` row with `submission_type='sample_request'`, and it explicitly shares the exact same shared cut sheet step of the wizard that bulk orders use, writing into `apply_cut_sheets` with the identical `sheet_data.components[]` structure. Path two is a direct insert into the older, separate `sample_requests` table, which has no cut sheet linkage at all, storing only a flat `size_breakdown` JSON field with no versioning and no compatibility with the cut sheet editor tooling used elsewhere.

The audit's specific finding on structural parity is conditional: a sample request created through the public wizard, path one, does now match a bulk order's cut sheet structure exactly, confirmed by direct comparison of what the cut sheet manager component reads against what the submission hook writes for both cases. A sample request created directly against the older table, path two, still has no cut sheet object at all and cannot be opened in the same cut sheet editing tools. Both kinds of request appear merged together in the same merchandiser sample dashboard.

Approving or rejecting a sample previously had a live, silent bug: the code built a database filter referencing a reference code column that did not exist on the older `sample_requests` table, which Postgres rejected outright, and that rejection was swallowed by an empty catch block, so clicking Approve or Reject for that class of sample never actually saved anything while still appearing to succeed. This was fixed in `supabase/migrations/20260830000000_sample_request_reference_code.sql` by adding the missing column and rewriting the update logic to look the record up by its own source table and ID directly rather than by that filter.

Converting an approved sample into a real bulk order requires both a Master SKU and a Quote Number to be entered first, a rule enforced only in the browser; the underlying database function that performs the conversion, `convert_sample_to_work_order()`, does not itself check for either value, so a direct call to that function would bypass the requirement entirely.

### 5.4 Price Quotes

**In plain terms:** Before a bulk order is confirmed, a merchandiser can send the customer a formal price quote breaking down labor, wash, and trim costs plus margin, which the customer can then accept or reject.

**Technical detail:** `src/components/merchandiser/PricingQuoteModal.tsx` starts every cost field at zero and requires the merchandiser to manually enter a real labor cost and a real margin percentage before the quote can be sent; nothing is pre-filled. A rush multiplier is shown for context only and an explicit code comment confirms it is never automatically applied to the calculated price. No hardcoded pricing or fallback value of any kind was found feeding into this live calculation. The `price_quotes` table's numeric columns default to zero purely as a database safety net, a default the interface never actually allows to be submitted.

A hardcoded price does exist elsewhere in the codebase, but not in this live flow: the dead, unused top level `useConvertSubmission.ts` hook described in section 4.7 computes a total contract value as quantity multiplied by a flat $24.50, a value confirmed to never actually reach a real user because nothing imports that file.

### 5.5 PO Dropdown Filtering

**In plain terms:** When a customer files a request to revise an existing order, the dropdown offering their active purchase orders to choose from is meant to show only their own company's orders.

**Technical detail:** `src/components/apply-portal/subforms/UpdateOrderSubform.tsx` combines two data sources with two different filtering approaches. Purchase orders from the `purchase_orders` table are filtered at the database query level by an exact match on the customer's company ID. Submissions from `apply_submissions`, however, are fetched with no server side filter at all and then filtered afterward in the browser, matching either an exact email address or a loose, case insensitive substring match of the company name in either direction. This second filter is purely an interface level convenience; it depends entirely on the underlying row level security on `apply_submissions` to actually prevent one company from ever seeing another company's rows in the first place, which, as documented in section 1.3, is currently not fully closed.

### 5.6 Rush Delivery

**In plain terms:** A customer or a merchandiser can flag an order as a priority rush job, which pulls the expected delivery date forward and applies a price multiplier an admin controls, though the flag does not currently do anything to actually reorder the physical work queue on the factory floor.

**Technical detail:** The configurable fields, `tenant_config.rush_multiplier` and `tenant_config.rush_lead_time_reduction_days`, are set only by an `admin` or `super_admin` on the branding and operational limits settings page, and were confirmed in the responsible migration's own comment to have replaced what used to be a hardcoded 2.0 times multiplier baked directly into the review screen. A customer can choose Rush versus Normal priority for a bulk order at the final review step, reading the live admin configured multiplier rather than any fixed value, and a merchandiser can override the choice during conversion. The only confirmed downstream effect is that a rush order's suggested factory ship date is pulled forward by the configured number of days when a merchandiser is picking a due date, and that the flag is surfaced as a badge in various submission lists. No dispatch queue reordering, shop floor priority lane, or automatic notification tied to the rush flag was found anywhere in the codebase; today it is informational and a scheduling input only. A separate, dedicated "Rush Order" intake flow appears to have been planned and abandoned; a placeholder component, `RushOrderSubformStub.tsx`, still exists in the repository reading "currently under maintenance, coming soon" and is confirmed unreferenced from anywhere else.

### 5.7 Order Status Editing and the Security Fix

**In plain terms:** Earlier in the project's history, the database rule protecting orders from being edited was accidentally left wide open, meaning anyone visiting the site, without logging in at all, could have changed any order's status, quantity, or customer name, or created fake orders outright, using nothing more than the public key that ships in the website's own code. This has since been fixed, and this section explains exactly what was wrong and exactly what changed.

**Technical detail:** The vulnerable policies, created in `supabase/migrations/20260808000100_fix_all_rls_recursion_and_pipeline.sql`, granted the `anon` database role, meaning an unauthenticated visitor, both `INSERT` with no real check and `UPDATE` with a condition of literally `USING (true)`, which in row level security means the condition always passes for every row. A companion `SELECT` policy used a helper function that itself returned true unconditionally whenever the caller was not logged in at all. A later migration added a second, properly scoped set of policies alongside these, but because Postgres combines multiple permissive row level security policies with OR logic rather than replacing them, the forgotten wide open policy continued to dominate and the newer, correct policy had no actual effect, a pattern the fixing migration's own header describes as meaning "the table has effectively had no real access control this whole time." The identical pattern was found and fixed on nine other tables in the same pass, `cut_tickets, sewing_tickets, customers, materials, cutting_records, sewing_bundles, wash_batches, cartons`, and `notifications`.

The fix itself was two migrations. `supabase/migrations/20260901000100_close_forgotten_anon_rls_holes.sql` explicitly dropped the four forgotten policies on `orders` by their exact names, leaving only the already existing, properly scoped policies in effect and removing the `anon` role's access entirely. `supabase/migrations/20260901000200_role_granular_rls_matrix.sql` then went further, replacing the coarse staff policy, which had treated every non-customer role as equally trusted, with the granular `has_module_permission('orders', 'update')` check described in section 2, so that today only `super_admin, admin`, and `merchandiser` roles can update an order at all, and no anonymous caller can reach the table in any capacity.

A closely related, still open issue was found while auditing this exact fix: the `apply_submissions_select_all` policy from the same original, wide open batch was never dropped by any later migration, meaning, unless it has since been closed outside the migration history captured in this repository, any anonymous visitor can currently read every customer submission, including contact details and internal notes, through the same mechanism that was just described as fixed for orders. This is recorded in full in section 1.3 and again in the consolidated gap list in section 13, because it is functionally the same class of vulnerability as the one this section otherwise describes as resolved.

### 5.8 Known Gaps

- `apply_submissions_select_all`, granting any anonymous visitor full read access to every customer submission, was never dropped and, unless closed outside this repository's migration history, remains open today. See sections 1.3 and 5.7.
- `bundles_full_access`, `scan_events_full_access`, and `inventory_issuances_full_access` grant any visitor full read and write access to those three tables, for the same reason.
- The sample request approve and reject bug against the older `sample_requests` table, described in section 5.3, is fixed, but the underlying pattern, a database write error silently swallowed by an empty catch block while the interface still reports success, was found again elsewhere in the codebase and is worth treating as a class of defect rather than a single incident.
- The dead `useConvertSubmission.ts` hook, containing a hardcoded $24.50 per unit price and several other fabricated fallback values the project's own plan called for removing, still exists in the repository even though it is never called.
- No server side check exists on the database function that converts a sample into a bulk order, confirming that the Master SKU and Quote Number requirement described in section 5.3 is a frontend convenience only, not a real guarantee.
- Rush delivery is currently informational only past the ship date calculation described in section 5.6; it does not reorder any actual production queue.
- A placeholder "Rush Order" intake subform still exists in the repository, unreferenced anywhere, suggesting a planned dedicated rush intake flow that was never built.

## 6. Quality Control

### 6.1 AQL Inspection

**In plain terms:** Acceptable Quality Limit, or AQL, inspection is a standard statistical sampling method used in garment manufacturing, where an inspector checks a mathematically determined sample size out of a full shipment lot and the shipment passes or fails based on how many defects turn up against a published acceptance table. Forge and Fabric names one of its quality checkpoints "Final AQL-Packing Audit," but a full search of the codebase found no actual statistical sampling logic anywhere in the system.

**Technical detail:** A repository wide, case insensitive search for the term AQL turns up matches only as the literal text of a checkpoint label, in `qc.tsx`, `reports.tsx`, and `qcGateValidation.ts`. A further search for `sample_size`, `acceptance_number`, `aql_table`, `lot_size`, or `sampling_plan` returns zero matches anywhere in the source code or the database migrations. In practice, "AQL" in this system functions as nothing more than the name of one of five quality checkpoints, mechanically identical to every other checkpoint, where an inspector manually types in whatever inspected and failed quantities they observe, bounded only by the total quantity on the record being inspected. There is no enforced minimum sample size derived from an actual lot size, and no ANSI or ASQC style sampling table implemented anywhere.

### 6.2 Cost of Poor Quality (COPQ) Tracking

**In plain terms:** Every time a quality inspector flags a batch of garments for rework, the system automatically calculates a dollar cost for that rework, based on labor time and any fabric wasted, and rolls those figures up into a report so management can see where quality problems are actually costing the most money.

**Technical detail:** The data lives in `rework_logs`, populated exclusively from the rework branch of the Log QC Inspection form in `qc.tsx`, and only when an inspector marks the overall result as Rework. Its cost column, `calculated_copq_usd`, is a Postgres generated column, computed automatically and unchangeably by the database itself from the formula `(labor minutes divided by 60, times an hourly labor rate) plus (scrap yards times a cost per yard)`, using a default labor rate of $18.00 per hour and a default fabric cost of $6.50 per yard, since the live insert from `qc.tsx` never overrides either rate per row. It is surfaced only on the `/reports` page, in a dedicated "Cost of Poor Quality Financial Tracking" card showing total dollar loss, total rework labor hours, total scrap fabric consumed, and the top defect types driving cost, none of which appear anywhere on the `/qc` page itself where the data is actually entered.

### 6.3 Goods Receipt Note (GRN)

**In plain terms:** A Goods Receipt Note is the record created when raw fabric or trim physically arrives at the factory and is logged in, checked, and either approved for use or placed on hold.

**Technical detail:** Two nearly identical screens implement this flow independently, `/materials` and `/inventory`, both covered fully in section 8. A GRN submission writes into the legacy `materials` table and, separately, into the modern `inventory_lots`/`inventory_items` tables at the same time, and, if the referenced purchase order does not already correspond to an existing order, silently creates a new placeholder `orders` row with a generic customer name as a side effect, so a materials desk employee can inadvertently create a brand new order record just by logging a delivery. Setting a lot's inspection status to Approved is the specific action, restricted to `admin, super_admin`, and `warehouse` roles only, that unlocks the fabric lot lockout on the cutting floor described in section 3.3, so this one status field is the actual hinge point between the receiving desk and the cutting room being allowed to start work.

### 6.4 Summary Table of Every QC Gate

### 6.5 Known Gaps

- No actual AQL statistical sampling logic exists anywhere in the system, despite a checkpoint explicitly named for it; every inspection quantity is entered manually with no enforced minimum sample size. See section 6.1.
- Two separate, disagreeing sets of minimum stage thresholds exist for the same five quality checkpoint names, one in `src/lib/qcGateValidation.ts` and one hand rolled directly inside `qc.tsx`, meaning whether a given checkpoint can be logged at a given stage depends on which screen the inspector happens to be using.
- An inspector with edit permission can freely change any inspection's result between Pass, Rework, and Reject through a dropdown after the fact, with none of the sequential gate or ticket existence checks re-applied to that edit; those protections only run at the moment a new inspection is first created.
- Several writes in `qc.tsx`, including the insert into `rework_logs` that feeds the cost of poor quality figures, are wrapped in error handling that only logs a warning to the browser console on failure, so a failed cost record can be silently lost while the interface still reports the inspection as saved.
- A hardcoded fallback list of quality inspections is shown whenever both the live and cached inspection lists are empty, indistinguishable in the interface from real data.
- The reports page's defect distribution chart falls back to fabricated defect names and dollar figures whenever the real rework log data is empty.
- The barcode scanner kiosk at `/tablet` can log a Pass or a Rework quality result directly with no gate validation of any kind, a bypass path for the sequential checkpoint rules enforced everywhere else, described fully in section 7.2.

## 7. Operational Portals

### 7.1 Cutting Portal

A full plain language and technical description of the cutting portal, including its screens, gates, and outsourcing behavior, is given in section 3.3, since cutting is entirely a shop floor implementation of pipeline stages 5 and 6. This section adds only what section 3.3 did not already cover: the daily user experience and realtime behavior.

**In plain terms:** A cutting room supervisor's day on this screen starts by checking which work orders are ready for cutting, opening a new ticket against an approved fabric lot, and marking tickets complete as bundles are physically finished, watching the bundle barcode chips populate on each ticket card as work is done.

**Technical detail:** No `.channel()` realtime subscription exists inside `cutting.tsx` itself; data is loaded once when the page opens and refreshed only after the user's own actions, such as creating or completing a ticket. A second supervisor working the same screen at the same time would not see the first supervisor's changes without manually reloading the page.

### 7.2 Sewing Portal and the Barcode Scanner Rebuild

A full description of the sewing portal's stage 7 gates and ticket based workflow is given in section 3.4. This section documents the barcode scanning system specifically, since it was substantially rebuilt and the audit found the rebuild left two disconnected systems both claiming to represent sewing progress.

**In plain terms:** Forge and Fabric has two entirely separate ways of recording sewing progress that do not talk to each other. The modern one, the ticket system described in section 3.4, is what actually controls whether an order is allowed to leave the sewing stage. The older one, a barcode scanning kiosk screen, still exists, still looks fully functional, and still writes data to the database, but none of what it writes is ever read by the rule that decides whether an order can advance. An operator using the kiosk today can complete every step it offers and have it have no effect at all on the order's real progress.

**Technical detail:** The kiosk lives at `/tablet` (`src/routes/tablet.tsx`, 499 lines), described by its own migration comment as what `sewing.tsx` used to be, before the ticket concept existed, when it "was a barcode-scan page with no ticket concept at all." The rebuild replaced `sewing.tsx`'s entry point with the ticket based flow in section 3.4, but left the original scanner screen in place, unmodified, still pointed at the pre-ticket data model.

Tracing a physical scan event end to end: an operator scans or types a barcode into an auto-focused text field, which triggers `handleLookupBundle()`, querying the `bundles` table for a matching `bundle_barcode`. If no row matches, including while genuinely connected to the live production database, the code does not show an error; it falls through to a hardcoded, fabricated demo bundle, complete with an invented work order number, colorway, size, and quantity, and shows the operator a success message stating the bundle was loaded. From that point, four action buttons are available: Start Work Order, which sets the bundle's status to `In_Progress` and inserts a row into `scan_events`; Log QC Pass, which inserts a `Pass` row into `qc_inspections`; Flag Defect & Rework, which inserts a `Rework` row into `qc_inspections` and sets the bundle to `Rework`; and Complete & Advance, which sets the bundle to `Passed` and inserts a final `scan_events` row. None of these four actions ever write to `sewing_tickets`, call the stage advancement check, or run any of the duplicate ticket or sequential checkpoint validation described in section 6, meaning a scan that appears completely successful on screen, including the demo bundle scenario above, has zero effect on the order's actual ability to move to stage 8.

**Known gaps, specific to this screen, beyond the disconnection described above:** the recent scans list shown on the kiosk is seeded with two fabricated example entries at page load, and a row of clickable "Quick Test Barcodes" sits directly on what is otherwise styled as the live production kiosk screen, with no visible indication that these are demo aids rather than real shortcuts. No realtime subscription exists for this screen either.

### 7.3 Wash and Finishing Portal

A full description is given in sections 3.6 and 3.7, since wash and finishing are implemented as a single screen covering stages 9, 10, and part of 11. No realtime subscription was found in `wash.tsx`; the same manual refresh behavior described for cutting in section 7.1 applies here.

### 7.4 Dispatch Portal

A full description is given in section 3.10. No realtime subscription exists in `dispatch.tsx` either.

### 7.5 Tablet Kiosk and Shop Floor Dispatch Board

The tablet kiosk itself is covered in section 7.2. A separate, smaller screen, `/shop-floor` (`src/routes/shop-floor.tsx`, 125 lines), is a minimal internal job dispatch board, showing which work orders are cleared for production versus blocked waiting on materials, using `current_stage_id >= 2` as a rough stand in for whether materials have actually been issued, with an explicit code comment admitting this is "assumed... for demo purposes" rather than a real materials issuance flag. Its two action buttons, Open Job Card and Request Materials, have no click handler wired to either of them at all, meaning they are entirely decorative.

### 7.6 Realtime Behavior Summary

**In plain terms:** Only two of the operational portals actually update live for a second person watching the same screen without them refreshing the page. Every other operational screen requires a manual reload to see another user's changes.

**Technical detail:** Confirmed by directly searching every relevant file for a `.channel()` call. `materials.tsx` subscribes to all changes on the `materials` table and refetches on any event. `useAppData.tsx`'s shared `db-realtime` channel, which most pages consume indirectly, covers `notifications, orders, qc_records, cartons, work_orders, stage_outsourcing_records, outsource_return_qc, blanket_pos, invoicing_records`, and `customers`, so any screen reading those specific tables through the shared hook does get a live update. `cutting.tsx`, `sewing.tsx`, `wash.tsx`, `dispatch.tsx`, `qc.tsx`'s own directly entered inspections, `inventory.tsx`, and `boms.tsx` have no `.channel()` subscription of their own for their primary record tables (`cut_tickets, sewing_tickets, wash_batches, packing_lists, qc_inspections, inventory_lots, boms`), meaning two people working the same shop floor screen at once will not see each other's changes without reloading.

### 7.7 Known Gaps

- The barcode scanner kiosk at `/tablet` is functionally disconnected from the sewing ticket system that actually governs stage progress, described fully in section 7.2, and this is the single most consequential finding in this section.
- The kiosk fabricates a fake bundle record on a failed barcode lookup, even while genuinely connected to the live database, and shows the operator a success message for a scan that matched nothing real.
- The shop floor dispatch board's two primary action buttons are not wired to anything.
- Most operational portals, cutting, sewing's ticket flow, wash, dispatch, and direct QC inspection entry, require a manual page reload to see another user's concurrent changes.

## 8. Supply Chain and Master Data Screens

### 8.1 Inventory

**In plain terms:** This screen is a facility wide, lot by lot ledger of every fabric, trim, packaging, and chemical delivery on hand, letting warehouse staff log new deliveries against a purchase order and track how much of each lot is on hand, allocated to a cut ticket, and still available.

**Technical detail:** `src/routes/inventory.tsx` (1,087 lines), reading and writing `inventory_lots` and `inventory_items`. A Receive Material button opens a GRN modal, described in section 6.3, and a status dropdown per lot lets staff move a lot between Pending, Approved, and Hold, with Approved restricted to `admin, super_admin`, and `warehouse`. Access to the page's create and edit actions is gated by role or by `usePermission("inventory", "update")`.

**Known gaps:** the facility name shown for every lot is hardcoded to the literal string "Main Sewing Facility" regardless of the lot's actual facility, making the facility filter on this page non-functional in practice. There is no real foreign key linking a lot back to the purchase order or order it was received for; the connection is inferred by parsing a "(Lot: X)" pattern out of a free text description field on the older `materials` table, an explicitly documented fragile convention rather than a real relationship. A missing four point inspection score silently defaults to the number 12 rather than showing as blank, misrepresenting real inspection data. Receiving material against a purchase order the system does not already recognize silently creates a brand new order record with a generic placeholder customer name as a side effect. No realtime subscription exists on this page.

### 8.2 Materials Receiving

**In plain terms:** A near duplicate of the Inventory screen above, oriented specifically around the quality control decision, whether a delivered lot is approved for use in production, rather than pure warehouse bookkeeping.

**Technical detail:** `src/routes/materials.tsx` (1,108 lines), independently reimplementing most of the same goods receipt logic as `inventory.tsx`, including the same silent placeholder order creation behavior. Approving or holding a lot here additionally writes a `qc_records` row tagged "Raw Material QC" and, on approval, advances the matched order to stage 4 both locally and in the database. This is the one operational screen in this section that does have a live realtime subscription, refetching automatically whenever the `materials` table changes anywhere.

**Known gaps:** the status update handler on this page attempts to write to a column, `inventory_lots.qc_status`, that does not exist anywhere in the actual database schema; every call to this code path fails, and that failure is caught and only logged to the browser console, so the interface shows a success toast for an update that never actually happened. The role list gating the Receive Material button on this page differs slightly from the equivalent list on the Inventory screen, an inconsistency between two screens that are meant to represent the same underlying action.

### 8.3 Machines

**In plain terms:** This is not an operational tool at all. It is a static, public marketing page listing the factory's physical equipment with photographs, reachable by anyone without logging in.

**Technical detail:** `src/routes/machines.tsx` (91 lines), rendered under `PublicLayout`. Every machine name, description, and image path is hardcoded directly in the component; a repository wide search confirms there is no database table backing this page in any form. If the business intends to eventually track machine capacity, uptime, or line assignment for production planning purposes, that capability does not exist anywhere in the codebase today; this page only lists equipment for visitors to read about.

### 8.4 Bills of Materials (BOMs)

**In plain terms:** This screen lets a merchandiser define, for a given style and optionally a specific colorway, which raw materials go into a garment, in what quantity, and with what waste allowance, and shows a rough estimated material cost per garment.

**Technical detail:** `src/routes/boms.tsx` (513 lines), reading and writing the `boms` table, joined to `styles` and `inventory_items`. Gated on `usePermission('product_master', 'update')`.

**Known gaps:** the estimated unit material cost shown prominently on every style's summary card is entirely fabricated, computed from a hardcoded flat rate, $4.50 for anything categorized as Fabric and $0.25 for everything else, with an explicit code comment calling it a "Costing estimation stub," since no real per item cost field exists anywhere in the schema. A second, different pair of hardcoded rates, $5.50 and $0.35, is used as a fallback default elsewhere in the same file, meaning two inconsistent fabricated price assumptions coexist in one screen. The Add Material Line modal's "Material Category" dropdown is mislabeled; its options are actually units of measure, not material categories. At the database level, the write policy on this table only checks that a user is any internal staff member at all, not the more specific `product_master` permission the interface itself enforces, so the interface's read only restriction for some roles could be bypassed by a direct database call.

### 8.5 Size Ranges

**In plain terms:** A simple master list of reusable size scales, such as numeric denim waist sizes or letter sizes small through triple extra large, that get assigned to styles elsewhere in the system.

**Technical detail:** `src/routes/size-ranges.tsx` (434 lines), full create, edit, and delete against the `size_ranges` table. Gated the same way as BOMs, on `product_master` update permission, with the same database level gap of only checking general internal staff status rather than the specific permission.

**Known gaps:** a second, entirely separate sizing concept, `size_templates`, used by the customer intake wizard, exists in the schema with no integration or reconciliation with this master list at all, meaning the system runs two parallel, non-connected sizing systems. Deleting a size range that is still in use by a style will fail at the database level, but the interface shows only a generic, unfriendly error message rather than explaining the conflict.

### 8.6 SKU Mapping

**In plain terms:** This screen translates a customer brand's own style or SKU reference, as written on their paperwork, into the factory's internal code, so cut tickets and bills of materials can be routed correctly. A customer logged into their own account sees only their own brand's mappings.

**Technical detail:** `src/routes/sku-mapping.tsx` (720 lines) and `src/hooks/useSkuMappings.ts` (409 lines), reading and writing `sku_mappings`, with a live realtime subscription on both that table and `orders`.

**Known gaps, and this is a significant one:** the database level row level security on `sku_mappings` was found to be effectively wide open. A fully permissive policy, `sku_mappings_full_access`, grants full read and write access to the public, anonymous, and authenticated roles alike with no restriction at all, and because it was added after an earlier, narrower policy pair without that narrower pair ever being dropped, it overrides them entirely under Postgres's OR combination rule for permissive policies, the identical mechanism described in section 5.7 for the fixed `orders` vulnerability. In practice, this means the "Tenant Isolated View" this screen presents to a customer is enforced only by JavaScript in the browser, not by the database, and any authenticated customer, or even an anonymous visitor, can read and write every other brand's SKU mappings directly. Separately, and independent of that security issue, any live order lacking an explicit mapping has one automatically fabricated for display, using a generated code such as `FF-WIE-SKUABCD`, indistinguishable in the table from a genuine, curated mapping apart from a small note. A hardcoded set of eight demo mapping records is also shown whenever the real table returns zero rows, again with no visual distinction from real data.

### 8.7 Known Gaps

- The `sku_mappings` table's row level security is effectively open to any visitor, described above, and should be treated with the same urgency as the `orders` and `apply_submissions` issues in sections 1.3 and 5.7.
- Both goods receiving screens, Inventory and Materials, independently reimplement the same logic with already diverging behavior, including one confirmed broken database write in the Materials screen described in section 8.2.
- The Bills of Materials screen's headline cost figure is entirely fabricated from two different, inconsistent hardcoded rate assumptions.
- The "Machines" page is decorative marketing content, not an operational equipment registry, despite its name suggesting otherwise.
- A fully built, schema backed Raw Materials Intake feature exists in the codebase, complete with its own realtime subscription, and is entirely unreachable from the application's navigation, confirmed by a repository wide search finding no import of its components or its hook from anywhere.

## 10. The Customer Facing Experience

### 10.1 Screen by Screen Walkthrough

This section follows the path a customer actually takes, from first arriving at the intake portal through tracking a finished shipment.

**Screen 1, the intake hub, `/apply`.** Three cards, New Order, Track Submission, and Request Revision, plus a Track Submission link in the header that opens a small modal collecting a reference code and email before navigating to the status page.

**Screen 2, starting a new order, `/apply/new`.** A five step wizard: Company & Contact, Order & Sizes, Cut Sheet Ticket, Document Vault, and Review & Submit. On return, the wizard checks local browser storage for a saved draft and offers to resume it.

**Screen 3, Company & Contact.** Collects company and contact details, checks whether the typed email matches a prior submission and shows an alert if so, and lets the customer pick their order type, a new bulk order, a sample request, or a request to update an existing order, each of which branches the wizard differently. Nothing is written to the database at this step; everything is held in browser memory and local storage until final submission.

**Screen 4, Order & Sizes, bulk orders only.** Blanket purchase order terms, then one editable style block per garment, including the service selection picker described fully in section 4.1, per service detail fields, a size matrix, and a trims list.

**Screen 5, Cut Sheet Ticket.** A component by component fabric and yield worksheet, with the ability to download a blank template, export the filled worksheet as a spreadsheet including live production stage progress pulled from the `get-cut-sheet-stage-progress` edge function, or print it.

**Screen 6, Document Vault.** Drag and drop or camera capture upload of tech packs, prototype photos, and swatches, with a mandatory final design or prototype image required before continuing.

**Screen 7, Review & Submit.** A summary of every prior step, a Normal versus Rush priority choice as described in section 5.6, two mandatory agreement checkboxes, and the actual submission, which uploads any pending files, inserts the real database rows, and navigates to the confirmation page.

**Screen 8, confirmation, `/apply/thank-you`.** Shows the customer their reference code and a static four step "what happens next" explainer.

**Screen 9, no login status tracking, `/apply/status/$referenceCode`.** Covered fully in section 10.2.

**Screen 10, requesting a revision, `/apply/update`.** Covered fully in section 10.3.

**Screen 11, the logged in customer dashboard, reached at `/orders`.** Shows metric tiles for active purchase orders, intake and sample requests, and completed orders, a table of active intake applications and sample requests with a Track Status link per row, and a table of purchase orders and contracts with a View Contract link into the order detail page.

**Screen 12, order approval, when a merchandiser has drafted an order on the customer's behalf.** Covered fully in section 5.2.

**Screen 13, account settings, `/account`.** Profile, company address, notification preferences, and password change, shared with staff accounts and adjusted per role.

### 10.2 Reference Code Tracking

**In plain terms:** A customer can check the status of their order at any time without logging in at all, using only the reference code they were given at submission and the email address on file.

**Technical detail:** The lookup is proven server side by a database function, `get_submission_status_by_reference()`, which runs with elevated privileges specifically so that the public `apply_submissions` table and its related tables never need to be opened to anonymous read access directly. A client side rate limiter in browser storage blocks further attempts after five failed tries in an hour, though this is trivially bypassed by clearing browser storage and is not a genuine server side protection. A live realtime subscription updates the page automatically if a staff member changes the submission's status while the customer is looking at it. On a mismatch, the error message is deliberately generic, not confirming whether the code or the email was the part that was wrong.

### 10.3 Update Requests From the Customer Side

**In plain terms:** A customer can ask for a change to an order or a sample at any time by filing a revision request, describing what they want changed.

**Technical detail:** The form tries the `submit-update-request` edge function first and silently falls back to a direct database insert, using a different set of column names, if the function call fails, meaning the two paths can produce structurally inconsistent records for the same kind of request. The success screen shows the customer a raw internal database identifier as their "Request Ticket ID" rather than the nicely formatted reference number the edge function actually generates for exactly this purpose, since the interface never reads that field from the response.

### 10.4 Language Audit

**In plain terms:** This document's requesting brief specifically asked whether any database, Supabase, SQL, or internal tooling language leaks into text a customer actually sees. This was checked directly against every customer facing file, and the answer is mostly no, with four specific, confirmed exceptions.

**Technical detail:** Every one of the following files was read in full for this check: `ApplyFooter.tsx, ApplyHeader.tsx, ApplyLayout.tsx, CameraCapture.tsx, CompanyInfoForm.tsx, CutSheetEditor.tsx, DocumentPreview.tsx, DocumentUploader.tsx, DraftRecoveryModal.tsx, FabricMaterialSelector.tsx, FactoryOneTemplate.tsx, MobileStepper.tsx, OrderClassificationSelector.tsx, OrderDetailsForm.tsx, PrintLayout.tsx, ProductTypeSelector.tsx, ReferenceCodeInput.tsx, RepeatableTrimsList.tsx, ReviewSummary.tsx, SameSampleTemplate.tsx, ServiceScopeSelector.tsx, SizeMatrixGrid.tsx, SizeTemplateManager.tsx, SpreadsheetGrid.tsx, StatusTracker.tsx, Stepper.tsx, StyleBlockEditor.tsx, SubmissionProgressModal.tsx, ThankYouPage.tsx, UpdateRequestForm.tsx, WeissmadeTemplate.tsx`, the four subform files under `apply-portal/subforms/`, `CustomerPortal.tsx, SubmissionReview.tsx`, every `apply.*.tsx` route, `account.tsx`, `useApplyDraft.ts`, and `useApplySubmission.ts`.

The four confirmed leaks are: `account.tsx` shows the literal sentence "You are currently running in mock mode. Password updates won't be saved permanently until connected to Supabase" to a logged in customer whenever the app is not connected to a real database, with no role check excluding customers from seeing it; an error thrown as "Not connected to the live database" can surface verbatim on the public status page if a price quote response fails; the public status page shows a customer's own revision request status as a raw, unformatted code such as "IN_PROGRESS" or "UNDER_REVIEW," underscore included, because the styling applied only changes letter case and does not remove the underscore; and the same page shows the request type as a raw internal code such as "spec_change" rather than the friendly label the customer originally selected from a dropdown. A fifth, related issue is not a database term leak but is a genuine display bug: the printed cut ticket shows the order type as "NEW_ORDER" or "SAMPLE_REQUEST" with the underscore visible, for the same reason.

No UUID was found rendered anywhere as a customer facing identifier; every reference a customer sees uses the formatted `APP-YYYY-XXXX` or purchase order style code instead. No internal table or column name was found interpolated into any customer visible text outside the specific exceptions above.

### 10.5 Known Gaps

- The four confirmed language leaks described in section 10.4.
- Three fully built subform components, for bulk order, rush order, and existing order update intake, are dead code reading "currently under maintenance, coming soon," confirmed unreferenced anywhere else, suggesting features that were planned and then abandoned mid build.
- Two cut sheet template components, `WeissmadeTemplate.tsx` and `SameSampleTemplate.tsx`, are fully built but never rendered by the cut sheet editor, which always uses a third template regardless of what type of cut sheet was intended.
- When a customer's existing purchase order dropdown returns zero real records, three entirely fabricated purchase orders are shown in their place, selectable for a revision request as if they were real.
- The post submission progress bar shown to a customer is a fixed, timed animation, not tied to the actual network requests happening behind it, and can visually finish before or after the real submission actually completes.
- The revision request type options a customer picks from do not match the values the rest of the system's type definitions expect, which directly causes the raw code display bug described above.

## 11. Technical Architecture

### 11.1 Frontend Stack

**In plain terms:** The application is built with React, using a newer set of tools called TanStack for page routing and data fetching, and a component library called shadcn built on top of Tailwind CSS for its visual styling.

**Technical detail:** React 19.2.0 provides the rendering layer. TanStack Router (1.170.16) and TanStack Start (1.168.26) provide file based routing and server side rendering; as documented in section 1.1, its route level guard mechanism, `beforeLoad`, is available but never used anywhere in this codebase. TanStack Query (5.101.1) is the data fetching and caching layer, configured centrally in `src/router.tsx`, detailed in section 11.3. shadcn's component conventions, layered on Radix UI primitives and Tailwind CSS 4.2.1, provide the visual component library, described in section 1.8 and again in section 12. Zod handles form and data validation. The `xlsx` package handles spreadsheet import and export for cut sheets.

### 11.2 Backend Architecture and Multi-Tenancy

**In plain terms:** All data lives in a single Postgres database managed by Supabase, and access to every row is controlled by database level security rules rather than by application code alone, at least in principle. A single settings table controls the one tenant's branding and a handful of operational limits.

**Technical detail:** The row level security strategy overall is documented fully in section 1.3, including the confirmed, currently open gaps on `profiles`, `apply_submissions`, `bundles`, `scan_events`, and `inventory_issuances`. Multi-tenancy in the strict sense of multiple independent factory tenants is not implemented; `tenant_config` holds exactly one row, meaning this deployment serves a single factory operator with multiple customer brands scoped underneath it by company, not multiple independent factory tenants sharing the platform.

### 11.3 Data Fetching and Caching

**In plain terms:** The application keeps a short lived cache of everything it fetches from the database, and when something changes on the server, most screens quietly ask for fresh data in the background rather than the server pushing the new values directly.

**Technical detail:** The global TanStack Query client, configured once in `src/router.tsx`, uses a ten second stale time, a five minute cache retention time, a single retry, and disables refetch on window focus and on reconnect. Individual hooks commonly override the stale time downward, to one second, for high churn shop floor tables such as orders, materials, and cutting records. Across every realtime subscription found in the codebase, ten distinct `.channel()` call sites in total, the pattern is completely consistent: a change event triggers `queryClient.invalidateQueries()`, causing a fresh fetch, rather than the new row being written directly into the cache. The one exception is `useSkuMappings.ts`, which uses its own manual refetch function instead of TanStack Query's invalidation mechanism.

### 11.4 Authentication and Authorization

**In plain terms:** A user's role is decided by their account record in the database and stored in the app while they are logged in. Whether a screen or button is available to them is then decided by checking that stored role, either against a list of allowed roles for a whole page, or against a permission table for a specific action. As documented in section 1.1, that check happens after a page has already started to render, not before, and as documented in section 1.3, the same permission table exists in two hand maintained copies, one in the browser and one in the database, that are not automatically kept in sync.

**Technical detail:** `src/hooks/useAuth.tsx` is the authentication provider, fetching the user's `profiles` row on sign in and holding it in React state. `usePermission()` and the `PERMISSION_MATRIX` in `src/lib/permissions.ts`, described fully in section 2, are the primary structured authorization tool the interface uses. Critically, the actual data queries feeding most screens, for orders, materials, and quality records among others, fetch the full table with no server side customer filter built into the query itself; a `customer` role user's view of only their own company's data is produced by filtering the already fetched, complete dataset in the browser afterward, inside `useAppData.tsx`. Whether this client side filtering is actually backed up by a matching row level security restriction on those specific tables, or whether it is the only thing standing between an authenticated customer account and every other brand's data, was outside the scope of the routes and hooks research and is exactly the kind of question the row level security findings in section 1.3 are meant to answer table by table; readers should cross reference that section rather than assume this client side filter alone is a security boundary.

### 11.5 Deployment

**In plain terms:** The application is deployed on Vercel as a single page application with a fixed set of security headers applied to every page. There is no separate staging environment; both development and the live site point at the same single Supabase database.

**Technical detail:** `vercel.json` defines a single, universal rewrite sending every path to `index.html` and a fixed header block including `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, a strict referrer policy, and HTTP Strict Transport Security, with no per branch or per environment variation. A repository wide search for the terms staging, preview as an environment concept, or `NODE_ENV` found nothing beyond a local development preview script in `package.json`. The single `.env` file at the project root and the hardcoded fallback credentials in `src/lib/supabase.ts`, described in section 1.9, reference the identical Supabase project, confirming there is exactly one database behind every environment this application currently runs in.

### 11.6 Planned Integrations: QuickBooks

**In plain terms:** A QuickBooks integration is mentioned as a future item in the project's own reference documentation, but no code, database table, or configuration for it exists anywhere in the application today.

**Technical detail:** A repository wide, case insensitive search for QuickBooks, QBO, or Intuit turns up genuine matches only in two planning documents, `PROJECT_REFERENCE.md` and the PDF version of the REQ-14/REQ-15 implementation plan, both stating plainly that this item, listed alongside two other planned integrations, Fishbowl and Ames360, is "explicitly Phase 3 roadmap" and "not implemented," requiring "external API credentials/OAuth setup" that does not yet exist. An identical comment appears in the header of one SQL migration file, `20260823000000_v2_spec_production_upgrade.sql`, stating the same thing. No document found anywhere in this repository describes a specific architecture for this integration, such as a per brand OAuth flow, a webhook handling design, or a particular QuickBooks subscription tier; the only architecture decisions the audit could locate were the bare statement that it is planned and the names of two other systems planned alongside it. Any more detailed architecture for this integration, if one exists, is not recorded anywhere in this codebase and should be treated as undocumented rather than assumed to match a description not found here.

## 12. Design System and UI

### 12.1 What Actually Changed Versus What Is Spec Only

**In plain terms:** A written design specification, `DESIGN.md`, describes an intended visual system for the app, and most of it has genuinely been built. One specific rule in that document, however, is knowingly not followed, for a documented reason, and this section separates what was actually built from what remains only a written intention.

**Technical detail:** `DESIGN.md`'s color token table matches the actual tokens defined in `src/styles.css` closely. Its rule that every authenticated screen, explicitly including `/apply`, `/apply/new`, and `/tablet`, must always stay wrapped in the app's shell navigation is not followed for the `/apply` family of routes; those routes render inside a separate, standalone header and footer instead. This is not an oversight; a code comment directly in `src/components/apply-portal/ApplyHeader.tsx` explains that wrapping them in the authenticated shell is not possible, because that shell hard redirects any visitor without a login session straight to the login page, which would break the public, no login order intake flow those same routes are built to serve.

### 12.2 Fonts

**In plain terms:** The interface is meant to use two typefaces, a general purpose one and a monospace one for code style numbers, both loaded from Google Fonts, though a small number of places on the site still use a third, unconfigured serif font as a decorative flourish.

**Technical detail:** `src/routes/__root.tsx` loads exactly two Google Fonts, JetBrains Mono and Plus Jakarta Sans. The CSS font stack also references SF Pro and Inter, but neither is ever actually loaded by the application, so on any computer that does not already have those fonts installed, which is most computers outside Apple's own devices for SF Pro, the browser silently falls back to Plus Jakarta Sans or a generic system font instead; the reference to SF Pro and Inter in the stylesheet describes an aspiration, not something the app actually delivers. Three separate places in the interface, the ampersand in the "Forge & Fabric" wordmark on the public layout and the login page, and a plus sign in a statistic on the landing page, use a plain, unconfigured browser default serif font as a decorative accent, a genuine inconsistency with the rest of the typographic system, though it appears to be a deliberate one-off flourish rather than leftover carelessness.

### 12.3 Emoji

**In plain terms:** The design specification explicitly forbids decorative emoji anywhere in the interface, and this was checked directly. The application code is clean; the only emoji found anywhere are functional country flags inside a phone number input, not decoration.

**Technical detail:** A search across every source file for the full range of common pictograph style emoji characters found none anywhere in the rendered application. The only emoji characters present at all are regional indicator flag emoji used functionally as country selector icons inside `src/components/shared/CountryPhoneInput.tsx`, which falls outside the design specification's own stated target of dashboard titles, buttons, and badges. The design specification document itself contains the literal forbidden emoji as illustrative examples of what not to do, which is expected and is not a violation of the rule in the running application.

### 12.4 Color Tokens

**In plain terms:** The application's colors are defined once, centrally, and most components pull from that central definition rather than hardcoding their own colors, though a few places bypass the system and hardcode the same colors directly instead.

**Technical detail:** Raw color values are defined under `:root` and `.dark` in `src/styles.css`, then aliased into Tailwind's own color namespace, and most components consume them as ordinary Tailwind utility classes such as `bg-primary` or `text-muted-foreground`. `AppShell.tsx`, however, mixes this token based approach with raw hardcoded hex values that happen to match the same underlying colors, meaning the same visual color is currently defined in two different places in that file rather than one.

### 12.5 Header and Back Button Logic

**In plain terms:** A single back button component appears in exactly two places across the entire application, the main app header and the public intake wizard header, and its behavior is consistent: it uses the browser's own navigation history to go back a real step whenever one exists, and only falls back to a fixed destination when there is no history to go back to, such as when a user arrived directly via a bookmarked link.

**Technical detail:** `src/components/BackButton.tsx` calls the router's `useCanGoBack()` hook and, when true, calls `router.history.back()`, genuinely returning to whatever the previous page was; only when there is no history does it fall back to a fixed `fallbackTo` route. The main app shell's usage of this component always falls back to `/dashboard` regardless of which of its 29 wrapped pages the button appears on, even for roles, such as quality control or production staff, that cannot actually access `/dashboard` and would immediately be redirected again. The public intake wizard's header, by contrast, computes a role appropriate fallback destination for a logged in user. The button's own default visual style is a plain grey pill that does not use the application's primary color or translucent glass styling at all, a minor visual inconsistency with the rest of the interface.

## 13. Known Gaps and Technical Debt Summary

This section consolidates every gap noted in the sections above, grouped by area, so the full risk picture can be read in one place.

### Security

- `profiles_select_clean` and `profiles_insert_clean` leave the `profiles` table open to full read access, and to insertion of a new row with an arbitrary role including admin, by any visitor, logged in or not. Section 1.3.
- `apply_submissions_select_all` and `apply_submissions_update_all` leave every customer submission open to full read and write access by any visitor. Sections 1.3 and 5.7.
- `bundles_full_access`, `scan_events_full_access`, and `inventory_issuances_full_access` leave those three tables open to full read and write access by any visitor. Section 1.3.
- `sku_mappings_full_access` leaves every customer brand's SKU mapping data open to full read and write access by any visitor, meaning the screen's "Tenant Isolated View" is a browser side convenience only, not a real boundary. Section 8.6.
- None of the twelve edge functions verify who is calling them beyond checking that an authorization header is present at all, and three, `get-cut-sheet-stage-progress`, `invite-user`, and `process-cut-sheet`, have no such check whatsoever; `invite-user` in particular can create a new admin account and is reachable by anyone who can reach its URL. Section 1.4.
- The now fixed `orders` table vulnerability, described in full in section 5.7, is documented here as a completed fix and as a template for recognizing the identical pattern in the still open items above.

### Data Integrity and Correctness

- Two different, disagreeing sets of minimum stage thresholds exist for the same five quality checkpoint names. Sections 3.5 and 6.5.
- Stage 11 has an internal naming and gate mismatch between what customers are told it means and what the database actually checks for it. Sections 3.7 and 3.8.
- `materials.tsx` attempts to write to a database column, `inventory_lots.qc_status`, that does not exist, silently failing every time while reporting success. Section 8.2.
- Two independently maintained copies of the "next stage" logic exist, one in the database and one in the browser, with no automated link keeping them in sync. Section 1.5.
- Two independently maintained copies of the full permission matrix exist, one in `src/lib/permissions.ts` and one hand transcribed into SQL, also with no automated link. Section 1.3.
- The bundle barcode generation scheme can produce identical barcodes across a genuine rework pass, and the insert logic silently overwrites the earlier bundle rather than distinguishing the two. Section 3.3.

### Features That Are Stubs, Fabricated, or Disconnected

- The barcode scanning kiosk at `/tablet` is functionally disconnected from the sewing ticket system that actually governs whether an order can progress, and it fabricates a fake bundle record on any failed lookup. Section 7.2.
- The Finance page computes every dollar figure from a hardcoded flat per unit rate with no connection to real pricing data, and never persists an invoice status change to the database. Section 9.3.
- The Reports page's three headline KPI tiles and its trend chart are hardcoded constants, not computed from real data. Section 9.2.
- The Dashboard's "Velocity & Quality Gates" widget is entirely hardcoded. Section 9.1.
- The Bills of Materials screen's headline material cost figure is fabricated from a flat, hardcoded rate assumption, with two different, inconsistent versions of that assumption coexisting in the same file. Section 8.4.
- No actual AQL statistical sampling logic exists anywhere despite a checkpoint explicitly named for it. Section 6.1.
- A fully built Raw Materials Intake feature, complete with its own realtime subscription, is entirely unreachable from the application's navigation. Section 8.7.
- The `send-notification` edge function, the only real email sending path for general notifications, is never actually called by the application, so several places that claim to have emailed a customer have not. Section 9.5.
- Three subform components for bulk order, rush order, and order update intake, and two cut sheet template components, are fully built and confirmed unreferenced from anywhere in the running application. Sections 5.6, 9.6, and 10.5.
- A dead, unused copy of the submission conversion hook still contains hardcoded fallback pricing and identifier values the project's own plan called for removing. Section 4.7.
- The database function that converts a sample request into a bulk order has no server side enforcement of the Master SKU and Quote Number requirement the interface presents as mandatory. Section 5.3.
- The Kanban board redesign described in the project's own implementation plan, adding service scope and outsourcing indicators to each order card, was not implemented; the helper function for it is imported but never called. Section 4.5.

### Silent Failure Patterns

- Across cutting, sewing, wash, quality control, and the goods receiving screens, a recurring pattern was found: a failed database write is caught and only logged to the browser console, never surfacing to the user and never rolling back dependent actions, so the interface can report success for an action that partially or entirely failed to save. Sections 3.12, 6.5, and 8.7.
- A previously live version of this exact pattern silently broke the ability to approve or reject any sample request created through the older, direct `sample_requests` table, until fixed by a dedicated later migration. Section 5.3.

### Customer Facing Language

- Four confirmed places where implementation language, the word Supabase, the phrase "live database," or a raw unformatted status or type code, reaches a customer facing screen. Section 10.4.

### Design and Consistency

- `/apply` route family intentionally does not follow the written design specification's rule that every authenticated route stay inside the main app shell, for a documented technical reason. Section 12.1.
- A decorative serif font appears in three places with no configured font backing it, an inconsistency with the rest of the typographic system. Section 12.2.
- Roughly half of the shadcn component library was given a translucent, glass style visual treatment, and the other half was left in its original, plain form, so the interface currently mixes two visual styles depending on which components a given screen happens to use. Section 1.8.
- The main app shell's back button always falls back to `/dashboard` even for roles that cannot access that page, while the public wizard's equivalent button correctly computes a role appropriate fallback. Section 12.5.

### Architectural Debt

- Three separate representations of a purchase order, `orders.PO_number`, `blanket_pos`, and `purchase_orders`, and two separate customer master tables, `customers` and `companies`, coexist with no enforced reconciliation between them. Section 1.2.
- Nine tables were built with active row level security and are confirmed, by a full repository search, to be read or written by no application code at all. Section 1.2.
- Four of the twelve edge functions in the repository are not part of the live request path at all, including one, `submit-application`, that was abandoned specifically because the deployed version was silently dropping customer submitted data without anyone noticing. Section 1.4.
- The database level stage gate trigger did not exist at all for a roughly nine migration span of the project's history, meaning for that period only frontend logic, not the database itself, prevented an order from skipping stages. Section 1.5.
